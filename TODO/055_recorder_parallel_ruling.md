# 055 — Recorder 並列化の設計裁定(100 Hz へ最後の 2.4×〜10×)

**Status: DRAFT(設計裁定待ち — ユーザーと方針合意してから発注書化する。実装は未着手)**
**仕様**: SPEC §6.4(保存系ロスレス)/ §12-5(a)フルレート持続・§12-6 burst(未達分の移管先)
**材料**: [archive/054](archive/054_root_sink_throughput.md) 結果節(2026-08-16 実測)

## 事実(054 実測 — これが裁定の材料)

- 単スレッド Recorder の到達点: **mini 41.5 events/s(実稼働)/ 62.3 /s(隔離)**。
  100 Hz に **2.4× 不足**。ELITPC(4 AsAd、2.2 MB/event)は **≈10 /s** で **10× 不足**。
- 内訳(C 後 16.06 ms/event): `PEventTPC` 充填(map insert 支配)6.25 ms /
  `tree_->Fill()`(圧縮含む)≈10.3 ms。IMT はブランチ 1 本ゆえ 6% しか効かない。
- 単発の改良は出尽くした(054 で C/A/B を消化)。**残る手はイベント間並列のみ**:
  イベント同士は独立なので、fill+Fill をイベント単位で並列化する余地は構造的にある。

## 裁定してほしいこと

1. **ELI-NP 初回実機テストの前に並列化をやるか**(コード凍結の時期に直結):
   - 案 X: 凍結して ELI-NP へ(初回テストの実トリガーレートが 41.5 /s を下回るなら
     実害なし。天井は counted・可視で silent ではない)。並列化は実機テスト後の
     フェーズで。
   - 案 Y: 並列化を先に済ませてから凍結(§12-5 フルレート持続 + §12-6 を宅内で
     クローズしてから現地へ)。
2. **並列化の形**(発注書化するときの骨子。候補は次の 2 つ — KISS 順):
   - 案 P1: **N 本の worker が (fill + 自分の TTree に Fill) → run 終了時にマージ**
     または part ファイルを worker 毎に分ける(run{N}_wK.root)。writer ロック不要で
     スケールするが、**出力ファイル構成が変わる**(grawToEventTPC 互換への影響を
     要検討 — part 分割は既にあるので「worker=part」と割り切れるか)。
   - 案 P2: worker は fill(PEventTPC 構築)まで並列、**Fill は単一 writer スレッド**。
     出力構成不変(互換の心配なし)だが、Fill 10.3 ms が直列に残るので上限 ≈97 /s
     (mini はぎりぎり、ELITPC は不足)。
3. **保留②(過負荷 stop の EOS 予算 5 s)**: 224 Mbps 実測で在庫吐き出しに 100 s 超。
   並列化で在庫が溜まらなくなれば消える問題か、それでも予算の SPEC 改訂が要るか。

## 追記(2026-08-16 ユーザー — 目標の再定義。裁定の前提がここで変わった)

- **100 Hz を目指すのは mini TPC のみ**。ELITPC は本システムの流用であり、100 Hz 相当
  (≈2.2 MB/event × 100 Hz ≈ 7 TB/日)は**ストレージが持たないので端から目標ではない**。
  → 054 の「ELITPC 10× 不足」は裁定材料から外す。埋めるべきギャップは
  **mini の 41.5 → 100 events/s = 2.4×** だけ。
- **計測環境の割引**: 054/053 の実測は M4 Pro(メモリ・ストレージ・CPU とも高速)。
  実環境(ELI-NP 現地マシン)はこれより悪い前提で設計する —
  ①worker 数は決め打ちせず設定可能にする ②現地で隔離プローブ
  (`soak_evidence_054/prof_054_probe.cxx`)を再計測してから本番値を決める
  ③2.4× ぴったりではなくマージンを取る(例: 設計上 3〜4× を狙う)。
- この前提での見立て: P2(fill のみ並列)は M4 Pro ですら上限 ≈97 /s で 100 に届かず、
  実環境ではさらに下回る → **実質 P1(worker 毎 TTree)一択に近い**。ただし mini は
  1 GiB パート分割が既に頻繁に起きるサイズ感なので「worker = パート」の割り切りが
  効きやすい(互換裁定は残る)。

## 追記 2(2026-08-16 — GET ゼロサプレッション調査。裁定の第 3 の選択肢)

zCoBo FW(ZC706)は**ゼロサプレッション対応済み**(pipeCtrl bit10/29 + AsAd 毎
`zeroSuppress` デバイス。現行 physics 設定は disabled・閾値 600 が種入れ済み。
`config_parameters.dox:132` / `CoBoNode.cpp:3083` / `hardwareDescription_zCobo.xcfg`)。
- root-sink の天井は items 数(map insert)にほぼ比例するため、**ZS が有効なら
  イベントが 1〜2 桁縮み、並列化なしで 100 Hz に届く可能性がある**。
  実験側が ZS を使う計画かどうかで P1/P2 の必要性が変わる — 裁定時に確認。
  **ユーザー裁定(2026-08-16、059)**: 優先は Unfolding > ゲイン正規化 > ZS。
  **スピードアップ(本チケット)が効けば ZS は不要**という方向 — つまり本裁定は
  「ZS に逃げない」前提で行う。
  **同日確定(061)**: Warsaw 実働責任者 Mikolaj は「1 ビットも変えたくない」姿勢で
  **ZS は事実上不採用**。第 3 の選択肢は消滅 — 100 Hz(mini)はソフト側の並列化で
  閉じるしかない。
- ただし ZS では **frameType 1 系(chan/bucket 明示)**になる。我々は対応済みだが
  実データ照合ゼロ(合成のみ)。ELI-NP で ZS を使うならそこが初検証。
- FPN チャンネルは閾値 0(常時読み)にしないとペデスタル計算の入力が消える。
  モニタの先頭 25 cell ベースラインも ZS 下では意味が変わる(壊れはしない)。
