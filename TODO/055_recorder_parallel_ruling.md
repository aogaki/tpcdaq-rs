# 055 — Recorder 並列化の設計裁定(100 Hz へ最後の 2.4×〜10×)

**Status: DRAFT(設計裁定待ち — ユーザーと方針合意してから発注書化する。実装は未着手)**
**仕様**: SPEC §6.4(保存系ロスレス)/ §12-5(a)フルレート持続・§12-6 burst(未達分の移管先)
**材料**: [archive/054](archive/054_root_sink_throughput.md) 結果節(2026-08-16 実測)

## 事実(054 実測 — これが裁定の材料)

- 単スレッド Recorder の到達点: **mini 41.5 events/s(実稼働)/ 62.3 /s(隔離)**。
  100 Hz に **2.4× 不足**。ELITPC(4 AsAd、2.2 MB/event)は **≈10 /s** で **10× 不足**。
- 内訳(C 後 16.06 ms/event): `PEventTPC` 充填(map insert 支配)6.25 ms /
  `tree_->Fill()`(圧縮含む)≈10.3 ms。IMT はブランチ 1 本ゆえ 6% しか効かない。
- 単発の改良は出尽くした(054 で C/A/B を消化)。**残る手はイベント間並列のみ**:
  イベント同士は独立なので、fill+Fill をイベント単位で並列化する余地は構造的にある。

## 裁定してほしいこと

1. **ELI-NP 初回実機テストの前に並列化をやるか**(コード凍結の時期に直結):
   - 案 X: 凍結して ELI-NP へ(初回テストの実トリガーレートが 41.5 /s を下回るなら
     実害なし。天井は counted・可視で silent ではない)。並列化は実機テスト後の
     フェーズで。
   - 案 Y: 並列化を先に済ませてから凍結(§12-5 フルレート持続 + §12-6 を宅内で
     クローズしてから現地へ)。
2. **並列化の形**(発注書化するときの骨子。候補は次の 2 つ — KISS 順):
   - 案 P1: **N 本の worker が (fill + 自分の TTree に Fill) → run 終了時にマージ**
     または part ファイルを worker 毎に分ける(run{N}_wK.root)。writer ロック不要で
     スケールするが、**出力ファイル構成が変わる**(grawToEventTPC 互換への影響を
     要検討 — part 分割は既にあるので「worker=part」と割り切れるか)。
   - 案 P2: worker は fill(PEventTPC 構築)まで並列、**Fill は単一 writer スレッド**。
     出力構成不変(互換の心配なし)だが、Fill 10.3 ms が直列に残るので上限 ≈97 /s
     (mini はぎりぎり、ELITPC は不足)。
3. **保留②(過負荷 stop の EOS 予算 5 s)**: 224 Mbps 実測で在庫吐き出しに 100 s 超。
   並列化で在庫が溜まらなくなれば消える問題か、それでも予算の SPEC 改訂が要るか。
