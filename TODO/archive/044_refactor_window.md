## タイミングの裁定(2026-08-15 ユーザー合意 — この順序が本チケットの本体)

```
043(ECC エラー可視化)→ 033(異常系セマンティクス)→ ★044 本窓 ★
→ P4 UI 実配線 → 031(24 h soak)→ ELI-NP 実機テスト
```

1. **独立した「リファクタリング期間」は作らない**。まとまった窓はこの 1 回、
   フェーズ境界(033 完了直後・P4 起票前)に置く。
   - 033 が run 経路コアに入る**最後の計画変更** — その後が構造を落ち着かせる自然な区切り。
   - P4 の UI 実配線は controller の REST/status 面の**上に**積む仕事 — 土台を先に整える。
   - 全ゲート green(cargo 415 / C++ 216 / vcobo 161 / UI 126)= リファクタの前提条件が
     いま揃っている。
2. **043/033 の中では相乗りのみ**(既存ルールどおり)。発注書で縛った差分に独立リファクタを
   混ぜない(diff レビューが濁る)。
3. **031(24 h soak)は必ず本窓の後**。soak は「実機に持っていく最終形」を検証すべきで、
   soak 後にコードを動かすと検証が無効になる。
4. **ELI-NP 実機テスト前は凍結**。出張直前・現地でのリファクタ厳禁 —
   「家で検証したバイトと同じものを持ち込む」価値が churn に必ず勝つ。実機で挙動が確定した
   **後**は逆に好機(実機ログという最強のオラクルが手に入る)。

1. **Fable が一括品質レビュー**(コードベース横断。diff 単位でなく、肥大・重複・ホットパス・

2. **1 テーマ = 1 連番チケット**(045 以降)で起票 → implementer に発注。記録主義どおり
   各チケットに結果節。
3. **受け入れの共通条件(全テーマ)**: **挙動不変 = 既存テストを 1 文字も変えずに全 green**
   (テストを変えたくなったらそれはリファクタではない — 別チケットに切り出して裁定)。
   `cargo fmt && cargo clippy --tests -- -D warnings && cargo test` + C++/UI ゲート。
4. 窓の総括(やったテーマ / 見送ったテーマと理由)を本チケットの結果節に記録して閉じる。

## ワークリスト(2026-08-15 横断レビュー 3 レーン → Fable 裁定)

**受け入れ条件の精密化**: production を動かすテーマ = 既存テスト無変更で全 green(従来どおり)。
**テスト資産を動かすテーマ** = assert 内容・カバレッジ・テスト件数が不変で全 green
(import/mod 行の機械的変更は可)。

**採択(→ 045〜049 として起票・実施)**:
- **045** decode.rs の二重確保解消(フレーム毎 557 KB の余分な確保+コピー = ELITPC レートで
  ~223 MB/s。単一ファイル・実 graw オラクルで裏取り可。**窓の最優先**)
- **046** S 級ハイジーン束: A) geometry `lookup_ref`(per-sample clone 解消 — AUX 入り
  ジオメトリで per-sample malloc が発火する潜在事故の予防)B) graw_writer の `.expect()`
  4 箇所を counted error に(production 唯一の panic 起点)C) `eos_quiesce_ms = 0` 拒否
  validation(033 裁定③)D) `bind_pull` の共通化(decoder/graw_writer で 18 行同一)
- **047** プロセス起動・終了の衛生: Rust 5 bin のボイラープレート共通化(tracing/SIGINT —
  「1 箇所直して 4 箇所忘れる」形の解消)+ vcobo-daq の SIGINT graceful 化(041 発見⑤、
  リポ既存イディオムの移植 10-15 行)
- **048** UI・コメント衛生: A) angular.json `externalDependencies` に `three`/`three/addons`
  (jsroot の Node 専用 dead import が原因の 2.38 MB+667 kB チャンク除去 — スクラッチで検証済み、
  dist 7.8→4.9 MB・初期バンドル不変)B) ResizeObserver ライフサイクルの共有ヘルパ
  C) ecc_bridge/fake_ecc の一次資料出典コメントの一元化(訂正 2 箇所編集事故の予防)
- **049** ECC 遷移表パリティテスト: MockTransport(Rust)と ecc_core.hpp(C++)の
  **意図的二重化**(036 事故駆動)を、共有 golden 表で両側から照合し将来のドリフトを
  CI で捕まえる(統一はしない — 言語境界 = ZMQ のみの規約を守る)

**見送り・移管(裁定理由つき)**:
- **controller.rs 分割(C3)** → **P4 見積もり後に再裁定**。レビュー実測: 責務は混在して
  おらず(Transport port / Sequencer 純ロジック / REST が連続ブロック)、問題は行数のみ。
  UI レーン実測で P4 の配線点は 1 箇所 = REST 層に大きく足さない公算大なら元が取れない。
- **E2E ハーネス共通化(834 行同一)** → **031 に移管**。031 自身が 3 番目の利用者になる
  (rule of three の発火点)。p3_error_paths.rs のコード内コメント自身が「共通化の判断は
  031/044」と明記 — 031 側の発注書に織り込む。
- **MockTransport↔fake_ecc の統一** → しない(意図的二重化 — 049 のパリティテストが正解)。
- **FakeComponent/Recorder の統合** → しない(必要による分岐。watch only)。
- **Handler 3 重化(~90 行)** → しない(安定 3 コンポーネントをまたぐ抽象は KISS 違反。
  SPEC にコマンドが増えるまで放置)。
- **`status_timeout` の意味整理** → リファクタではない(033-D の gone リストで実害解消済み。
  P4 で status 周りを触る際に SPEC 確認込みで再考)。
- **monitor の u16 毎 extend / receiver のリンク毎 2 回符号化** → 測ってから(SPEC 帰結含む)。
- framer / config 実コード / 依存の向き / エラー・ログ流儀 / UI の WS 集約と Run 制御土台 /
  テスト名・env ゲート = **レビューの結果、問題なし**(記録として明記)。
