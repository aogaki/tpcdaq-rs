#### 明示した許容差(暗黙のホワイトリスト禁止 — 発注書 §1)

無視フラグを**外して**走らせたときの差分総数で「この 2 つ以外に差が無い」ことを確認した:

| 無視したフィールド | 差分件数 | 理由 |
|---|---|---|
| `fDataSource` | **108**(= 1 件/エントリ) | 我々は **0 固定**(SPEC §6.4「C++ 版 tpcdaq と同じく 0 固定」)。実機オラクルは生ヘッダ由来の **1** |
| `fHitPatterns` | **432**(= 4 件/エントリ) | 我々は**未充填**(SPEC §6.4「C++ 版同様 — 生 graw がバックストップ」)。オラクルは 69 bit 中 68 bit 立ち |
| (両方無視) | **0** | ← **他のヘッダ全フィールドと 15,040,512 サンプル全値が一致**(108×5 = 540 = 上 2 段の合計、で尽きている) |

一致した項目: `fRevision` / `fEventTime` / `fReadOffset` / `fStatus` / `fMult[4]` / `fWindowOut` /
`fLastCellIdx[4]`、および全チャンネル(272/エントリ)の全サンプル `(bucket, value)`。

**チャンネルの並びは実際に違う**(SPEC §6.4 の想定どおり): 我々 = `(0,0)(0,1)(0,2)…`((aget,chan) 昇順)/
オラクル = `(0,0)(1,0)(2,0)(3,0)(0,1)…`((chan,aget) 昇順)。`--strict-order` を付けると
**108 件の「チャンネルの出現順が違う」**が出る = キー突き合わせにした判断が正しかったことの実証。

### 発見した不具合(**production は直していない — 親のチケット化待ち**)

**decoder の PULL が、入力に追いつけないとき上流 2 ソースの片方を run 丸ごと飢餓させる。**

観測(dev ビルド、2 ソース、`--rate-mbps 224`):

| 層 | 実測 | 判定 |
|---|---|---|
| receiver ×2 の出力(graw-writer リンクで計測) | 両方とも first batch `0.1197 s` / EOS `1.195 s` / 109 フレーム | **完全に足並みが揃っている** |
| receiver → テスト用 PULL(decoder を外す) | `source_id` 順が `0,1,0,1,0,1,…`。消費側に 20 ms の sleep を入れて**わざと遅く**しても `0,1,0,1,…` のまま | **ZMQ の fair-queue は正常** |
| receiver → **decoder** の PULL | `batches_in` が `{"0":26,"1":1}`(t=0.52 s)→ `{"0":72,"1":1}`(t=1.06 s) | **片側を消費していない** |
| decoder → root_sink | 片方の 108 フラグメントを全部出してから、もう片方の 108 が出る(先頭の 1 本目が **1.1〜1.4 s 遅れ**) | 既定 `build_timeout_ms`=1000 ms を超える |
| root_sink(ビルダ) | `events_complete=0 / events_incomplete=108 / late_fragments=108` | **ビルダは仕様どおり**(SPEC §6.3: 捨てずに incomplete + late で保全) |

- **再現条件**: decoder が入力レートに追いつけないこと。dev ビルドの decode は実測 ≈ 10 ms/frame で、
  2 ソース ×224 Mbps(≈ 5 ms/frame)に追いつけない → dev では **5/5 で発生**。
  release では decode が十分速く滞留しないため **3/3 で発生せず**(= 上の §12-4 が green)。
- **飢餓の向きは run 毎に揺れる**(cobo0 が飢える run も cobo1 が飢える run もある)= レース。
- **仮説(未検証、production を触らないため)**: `src/decoder.rs:58` の
  `POLL_TIMEOUT_MS = 2` で `pull.set_rcvtimeo(2)` を張った tight loop が、libzmq の
  fair-queue における「空になったパイプの非活性化 → 再活性化で列の最後尾へ」と噛み合い、
  滞留時に片側パイプへロックインする。**検証には production の 1 行変更が要るので実施していない**。
- **影響範囲**: mini(1 CoBo)には無関係。**ELITPC(2 CoBo × 2 AsAd)で decoder が一時的にでも
  遅れた瞬間に全イベントが incomplete 化する**ため、P3 以降で塞ぐ価値がある。
  §12-5(24 時間連続負荷)・§12-6(瞬発負荷)を 2 ソースで回すときは必ず踏む。
- 本ユニットでの扱い: E2E-B に **`cfg!(debug_assertions)` の明示 skip** を入れた
  (理由文つき。`cargo test --release --test p2_e2e` で走る)。**タイムアウトを緩めて誤魔化していない**
  (`--build-timeout-ms` は既定 1000 ms のまま)。

### 発注書からの逸脱

1. **E2E-B のリプレイをペーシングした**(`--rate-mbps 224` = SPEC §12 末尾「mini 100 Hz 相当」)。
   発注書 §3 は速度を指定していない(§2 の E2E-A だけが「全速」)。全速だと受信バッチが 8 MiB まで
   太って 2 ソースのずれがバッチ 1 個分(1〜2 s)開き、`build_timeout_ms` の意味が変わってしまう。
   実機は 2 CoBo が同一トリガで同時に送るので、目標レートの方が実機に近い。
2. **`compare_gdataframe` に `--strict-order` を足した**(発注書はキー突き合わせのみを規定)。
   キー突き合わせだけでは「決定性 = イベント内 (cobo,asad) 昇順」(発注書 §3)を**証明できない**
   (順序差が原理的に見えない)ため。既定 off の明示フラグ。
3. **片側要約行(`A:` / `B:`)を stdout に出すようにした**。発注書 §3 の「eventIdx 昇順」「CoBo 毎
   フレーム数一致」を TTree 実測から取るのに必要で、比較器が既に持っている情報を 1 行にしただけ。
4. **`Makefile` は `compare` ターゲット追記のみ**の指定だったが、`.PHONY` と `clean` にも
   `compare_gdataframe` を 1 語ずつ足した(ビルド生成物が消えないのは欠陥なので)。
   併せて `tools/root_sink/.gitignore` に 1 行(生成物をコミットしないため。発注書の所有権リストには無い)。
5. E2E-B の後片付けを `let _ = timeout(...)` から **`.expect()` による厳格待ち**にした
   (同一プロセスで 2 回走らせる以上、前の run のタスク残留を黙って見逃せないため)。
