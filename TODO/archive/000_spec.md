## 決めるべきこと(PROPOSAL が仕様書送りにした項目の全リスト)

1. **ヒスト集計の持ち主(最重要 — PROPOSAL §5 R10)**: Rust monitor か root-sink か。
   候補 = root-sink が集計しスナップショットを publish、monitor/UI は表示に徹する
   (条件: 保存系プロセス内の負荷分離〔別スレッド化〕の検証)。二重集計は不可(UI とファイルの不一致リスク)。
2. **ZMQ リンク毎のメッセージ形式**: 生フレーム / デコード済みイベントのシリアライズ。
   delila-rs の形式に揃える。イベント ID(run 番号 / eventIdx)の運び方を含む。
3. **JSONL スキーマ(Q1)**: run メタデータの項目表(configId, ジオメトリ, 出力ファイル一覧, カウント…)
   + 監査ログ + シフトコメント + psu TRIP の行形式。**書き手は controller 単一ライタ**、他は ZMQ 経由投稿。
4. **WS プロトコル**: UI 向けワイヤ形式の再定義 + クロス言語適合性テスト方式(C++ 版の方式を踏襲)。
5. **コンポーネント境界と設定スキーマ**: 各コンポーネントの責務・起動順・設定ファイル形式。
   複数 CoBo 構成(receiver N 台)の書き方を含む。
6. **root-sink 流用の手術範囲**: PUB 購読 → PULL ロスレス化、DELILA イベント形式 → TPC 形式、
   TTree 内容の RootWriter からの移植。GDataFrame(CeCILL)の third_party/ 隔離方針。
7. **R4 波高の定義の明文化**: 生 ADC(減算なし)、x レンジ 0–4096 固定、飽和率表示の要否。
8. **受け入れ基準の数値化(P5)**: 連続 N 時間 / drop 0 @ 100 Hz 相当負荷の N。
9. **検証項目リスト**: MTU 9000(CoBo・経路のジャンボフレーム対応)、受信側 NIC 構成
   (10GbE か CoBo 毎 NIC か)、AGET 読み出しデッドタイム実測(P5 で)。
