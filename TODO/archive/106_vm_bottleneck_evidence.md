# 106 — GET を VM で動かしていることが律速である根拠(ホスト側からの受動計測)

**Status: COMPLETED**(2026-10-08 起票・計測 Opus。ユーザー「ホストが貧弱で VM で走っているからダメという気はするが根拠がない」)

> **訂正(2026-10-12、一部だけ試験済み — [107](107_elitpc_host_setup.md) run 2 / 12)**: §末尾の「低レート時の約 1 s の最短間隔は VM 内の処理の前半に対応する」は誤り。
> - VM を使わない ELITPC(tpcdaq-rs ネイティブ)でも、同じ CAEN の NIM→TTL 変換器では 1 s の壁が残った(run 2)。
> - 変換器を交換すると消えた(run 12、4.53 Hz、最小 4.9 ms)。したがって **1 s の壁は変換器で、VM ではない**。
>
> 一方、本書の計測そのもの(VM が 1 事象あたり ≈ 5 コア秒を使う)と、高レート run 09-25 / 09-30 の 0.36〜0.38 Hz が VM の処理上限(≈ 0.4 Hz)に当たっていたという見立ては、**試験していないので保留**。
> 変換器を交換した後に VM で取り直していない。ELITPC への移行で、この上限は運用上は関係なくなった。

## 0. 構成(読み取りで確認)
- ホスト GDED: i7-4790(2014、4C/8T)、メモリ 7.7 GB、SSD 850 EVO、zCoBo 直結 NIC は MTU 9000 / 1 Gb/s。
- VM(VirtualBox `Ubuntu16.04LTS_ELINP`): **vCPU 2**、メモリ 4 GB、NIC はブリッジで**エミュレーション Intel 82540EM(e1000)**、データの書き込み先は**共有フォルダ** TPC_Share(= ホストの `~/Desktop/TPC_Share`)。

## 1. 方法
ホスト上で 10〜14 ms ごとに受動サンプリング(`reference/_spike/stop_0929/vmprobe.py`): zCoBo 直結 NIC の受信バイト数、VirtualBoxVM プロセスの CPU 時間(utime + stime)、最新 .graw のサイズ。取得には一切触れない。
受信バイトの塊(1 フレーム ≈ 562 kB)を事象とみなす。2 回: 900 s(42 事象)と 900 s(30 事象、うち前後に他の事象がない 19 事象で CPU の平均プロファイル)。

## 結果(2026-10-08 午後、10-07 開始の run 継続中)
1 事象あたり(42 事象すべてで同じ振る舞い):
| 段階 | 所要 |
|---|---|
| zCoBo → ホスト NIC(線上の 562 kB) | 11〜37 ms |
| .graw がディスクで伸びるまで | 12〜40 ms(転送とほぼ同時) |
| **VM の CPU** | **事象直後から約 4.25 s、1.1〜1.4 コアを使い続ける**(平時 0.07〜0.2 コア)= **1 事象 ≈ 5 コア秒** |

平均プロファイル(19 事象、250 ms 刻み、t = フレームが線上に現れた時刻):
```
-1.00..-0.25: 0.21-0.24 | +0.00: 1.43 | +0.25..+1.00: 1.35-1.39 | +1.25..+2.00: 1.13-1.29 | +2.25..+4.00: 1.06-1.12 | +4.25: 0.58 | +4.50 以降: 0.07-0.26
```
- 線上の転送もディスク書き込みも数十 ms で終わっていて律速ではない。**律速は VM 内の 1 事象あたりの処理(≈ 5 コア秒)**。
- VM は vCPU 2 本なので処理の上限は 2 / 5 ≈ **0.4 事象/s**。高レートの 09-25 / 09-30 の記録レート 0.36〜0.38 Hz はちょうどこの天井 = 104 で見た「高レートで待ち行列型に回復が遅れる」不感時間の正体。
- 低レート時の約 1 s の最短間隔は、処理の前半(+0.0〜+1.25 s、1.4 コア)で zCoBo が次を受け付けられないことに対応すると考えられる(前半が受信・保存、後半 3 s がオンライン表示などの別処理、という分け方は推定。VM 内のプロセスは見ていない)。
- 4 s 以上も 1.1 コアを使う処理は、VM のソフトウェア描画(vmsvga)でのオンライン表示の更新が典型。**VM 内の `top` でどのプロセスか確かめる**のが次の一手(ユーザー)。

## 対策
- 当座: VM の GET でオンライン表示(GetController の波形・ヒスト窓)を閉じる / 更新を止める。VM の vCPU を 2 → 4 に(ホストは 8 スレッド)。
- 本命: puppex(i9 10C/20T、125 GB)で tpcdaq-rs をネイティブに動かす。受信は吸い出し専用で、表示・解析は別プロセス(never-stop)なので、この型の不感時間は原理的に出ない。移行後に同じプローブで比較できる。
