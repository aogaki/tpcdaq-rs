### 1.2 Wiring diagram and socket types

```
CoBo k ──TCP:46005+k──▶ [receiver k] ──PUSH──▶ (PULL bind) [graw-writer]      lossless
                             │
                             └──PUSH──▶ (PULL bind) [decoder]                   lossless
                                             │
                                             └──PUSH──▶ (PULL bind) [root-sink] lossless
                                                              │
                                                              └──PUB──▶ (SUB) [monitor] ──WS──▶ browser
                                                                  histogram snapshot / latest built event / status   latest first
[controller] ──REQ/REP(JSON)──▶ each Rust component (state transition commands)
[controller] ──REQ/REP(JSON)──▶ [ecc-bridge] ──Ice(1.1)──▶ ECC:46002
[each component] ──PUSH──▶ (PULL bind) [controller]  logbook posts (§9)
```

- **Lossless path = PUSH/PULL** (back-pressure by a finite HWM), **monitoring path = PUB/SUB** (thinning allowed; drops are made visible by gap detection).
- **Lossless PUSH requires `ZMQ_IMMEDIATE`** (v1.4): libzmq by default creates the local
  queue at connect() time, and a send to a not-yet-connected peer also succeeds up to the HWM — "appearing to have sent" with the downstream absent
  is a violation of the lossless contract (making loss invisible). IMMEDIATE **queues only to peers whose connection is established**.
  Applied links: receiver→graw-writer / receiver→decoder / decoder→root-sink. The implementation is consolidated in the
  PUSH helper of zmq_helper (no scattering of the setting). It is not applied to the monitoring-path PUB (a link that may drop).
  An **intentional difference** from delila-rs's "all links PUB/SUB + HWM=0 unbounded buffer" (§14-4):
  at ~111 MB/s for ELITPC an unbounded buffer risks runaway memory, so bounded + a visible error is chosen.
- **The PULL side binds** (stable endpoint) and the PUSH side connects. By the per-peer FIFO of ZMQ,
  the per-source order is preserved (the basis of the correctness of the file order in graw-writer — per-AsAd files are
  a subsequence of the source stream, so this guarantee directly becomes the per-AsAd order guarantee).
- **No direct decoder → monitor link is provided** (a change from the PROPOSAL diagram, §14-2). The supply source for the event display and
  waveform view is consolidated into the built-event publish of root-sink. Reasons: (a) the problem of the "displayed event"
  fragments disagreeing with 2 CoBo disappears structurally, (b) aggregation and display see the same build result, (c) one fewer link.
  If root-sink dies the monitor also stops, but root-sink is the lossless storage path and once it dies the run cannot continue anyway.

### 1.3 Process model, state machine, run sequence

- The component state machine adopts delila-rs as is:
  `Idle -Configure→ Configured -Arm→ Armed -Start→ Running -Stop→ Configured`, `Reset` goes to Idle,
  on abnormality `Error` (left only by Reset). Commands are JSON over REQ/REP (§2.6).
- **root-sink and ecc-bridge have no REP command socket.** root-sink is data-driven
  (run open on the first Data, close on EOS from all sources — the RunState approach of delila-rs root_sink).
  ecc-bridge has only a REQ/REP dedicated to the controller.
- Run start sequence (executed by the controller):
  1. Assign the run number (§8.1) -> `Configure` to each Rust component (from downstream: graw-writer, monitor → decoder → receivers)
  2. `Arm` — **the receiver does bind + listen here** (the implementation point of listen-before-start)
  3. `Start{run}` — the writers prepare files, the receiver starts accepting
  4. Via ecc-bridge, **`reset` (= return the ECC to `Idle`) →** `describe → prepare →
     configure (DataLinkSet XML) → start`
     - **Always return the ECC to `Idle` at the head of every run (v1.12, user decision 2026-08-14)**: real operation
       (University of Warsaw) follows the practice of "**fully resetting for every run and starting from scratch**", and we match it.
       **The same path is taken even for the first run** (no branching by state).
     - **⚠ The `reset` of the real ECC has "go back one step (`EV_UNDO`)" semantics and is not a direct jump to `Idle`
       (v1.12 correction — found by TODO/034 in the real ECC source, confirmed on the ordering side)**:
       the transitions of `EV_UNDO` are only the two `Described→Idle` and `Prepared→Described`, and
       **there is no `EV_UNDO` from `Active` (= Ready/Running/Paused)**
       (`GetBench/src/get/rc/BackEnd.cpp:924` / `:250-270`). An undefined transition raises no exception and is
       **`Ignored` silently** (`StateMachine/src/dhsm/Engine.cpp:344`). Moreover
       `BackEnd::configure` is **silently skipped by the guard `if (state == ST_PREPARED)`**
       (`BackEnd.cpp:955-962`).
       → Issuing `reset` just once from `Ready` after `ecc stop` **does nothing, the following
       describe / prepare are silent, configure is skipped, and only `start` succeeds**.
       **`Ready → Idle` requires a walk-back of `breakup` (Active→Prepared) → `reset` (→Described) →
       `reset` (→Idle)**. The controller **looks at the current ECC state and walks back only as many steps as needed**
       (using the state of §8.2).
       **The ECC after `ecc stop` is `Ready`**, and `describe` is permitted only from `Off / Idle / Described`, so without this walk-back
       **the 2nd and later runs cannot be established**
       (the cross-run measurement of TODO/030 + the real ECC analysis of TODO/034).
       **The operator is not made to insert `POST /api/ecc/reset` by hand.**
     - With `configure` **the CoBo re-establishes the data link** (see the v1.12 note below), which is also
       consistent with the receiver semantics of "one connection per run". **If `start` is issued with the walk-back incomplete,
       `configure` is skipped, and the run starts without the CoBo re-establishing the link**
       (on the real machine the previous run's socket has been closed on the receiver side, so
       "Could not establish data link." appears = a visible failure, but in any case the run is not established).
     - The controller **always leaves the ECC-reported state right after `reset` in the audit (`ecc_state_after_reset`)**
       (not silent. If `"Ready"` appears on the real machine, it is a signal that the walk-back is not working).
     - **Component walk-back (v1.38, TODO/113 / v1.39, TODO/114)**: run start begins only after **the components too have been walked back to Idle**, not only the ECC.
       First, from upstream (receivers → decoder → graw-writer), everyone is examined with `GetStatus`, and only those that are not Idle are returned. `Reset` cuts off pending sends, so
       `Running` must always get a `Stop` before `Reset` (as in v1.6, a run that is not closed is not Reset). The decoder's `Stop` does not emit its own EOS
       (it emits it only when it has received the EOS of all receivers), so order and waiting are needed:
       - **All `Running`** (the chain is intact. Typical = only the controller died during a run and restarted): the previous run is closed with the **same 2 stages as the stop sequence** —
         first stage = the earlier of completion of the natural EOS or receive-quiescence (`eos_quiesce`) of all receivers → if not closed, `Stop` to all receivers (forced EOS) →
         second stage = wait for EOS propagation (observation point and upper limit `eos_timeout` are the same as the stop path) → `Stop` to the rest (and to the receivers too if the forced EOS was not fired).
         The ECC has been walked back before this (`stop` makes the zCoBo stop sending, and `breakup` closes the data link = natural EOS from EOF), so the first stage usually
         closes immediately, but the `Stop` of a receiver folds the drain immediately (unread data in the kernel receive buffer vanishes uncounted), so as in the stop path
         the `Stop` is issued **after confirming quiescence**. The result is one line at the head of the trace, `"eos: closed"` / `"eos: did not propagate within <ms> ms"`. **Even if it does not arrive, start is not stopped**
         (the termination clause of v1.12 applied on the start side: `warn!`, the cut-off of the later `Reset` is visible through `messages_abandoned` / `eos_abandoned`, and root-sink
         hits exit 6 on the first Data of the next run = correct detection). The reason for not stopping = there is no recovery means even if stopped (there is no REST that Resets a component, and it
         returns to the 113 situation of "start keeps failing until the process is restarted").
       - **Only some `Running`** (the chain was Reset midway): the EOS does not reach the end and cannot be observed, so it is not awaited. The head of the trace gets
         `"eos: not awaited — the chain is broken (not every component is Running)"` (`warn!`), and those `Running` get `Stop` → `Reset`.
       - Others (Configured / Armed / Error) get `Reset` only. Finally `Reset` is sent from upstream to everyone not Idle.
       The trace is audit `run/start.component_walk_back` (`"<name>: <state>[->Configured]->Idle"`, `[]` if everyone is Idle). If `GetStatus` is unreachable (before touching any), or
       `Stop` / `Reset` is rejected or unreachable, the run is not started and fails at stage `walk-back` (the message gives the target and the state remaining at that time). If `Stop` does not go through, it does not proceed to `Reset`.
       The stop contract (`ok` = completion of EOS and storage, Reset non-arrival in `notes`) is not changed.
       Basis = the measurement of 112 (start kept failing because of a Reset that did not arrive at stop) / the real machine of 114 (ELITPC, α 4.5 Hz, controller kill -9 at runs 58 / 60 →
       restart → start): even with the 113 "Reset immediately after Stop" the EOS got through before the REQ round trip at low rate, but 114 closed with the trace `eos: closed` confirmed by waiting,
       and graw = ROOT counts agreed. The waiting is so as not to rely on a race (pending sends accumulate = effective when downstream stalls).
       **run_stop of the previous run (v1.40, TODO/115)**: if even one Running existed, the walk-back writes the `run_stop` of the previous run (§9.2, `reason: "abort:controller-restart"`).
       The material (counters / files) is taken with `GetStatus` after the `Stop` of everyone and before any `Reset` (even on the path with only some Running, all `Stop`s are done first —
       graw-writer releases its file records at Reset). The run number is used only when the `GetStatus.run_number` of the components agrees among all that reported it
       (a mismatch or no report is not written and is left in the audit. The next_run of the state file can be moved by `run/next`, so it is not used. The last run_start of the logbook is for cross-checking only).
       It is written before the `run_start` of the new run, and also written if start fails later. audit `run/start.previous_run_stop` = `{"run": N|null, "notes": [...]}`
       (null if there was no closed run).
     - `Arm` may temporarily fail to bind while waiting for the previous run's socket to be released (the close of libzmq is asynchronous).
       The controller **retries with exponential backoff** and **always records the number of retries and the time taken in the audit
       (`arm_retries`)** (measured: worst case 4 attempts / 157 ms. Upper limit 6 attempts / 620 ms).
     - **If the run start sequence fails, `next_run` is rolled back** (the controller is the single writer).
       However, after `run_start` has been written to the logbook it is not rolled back. "Numbers may be skipped" (§12-11) is
       maintained, but **states in which numbers skip under ordinary operational use are eliminated**.
  5. Write the run_start record to JSONL (§9)
- Run stop sequence:
  1. ecc `stop` (the CoBo stops sending. **The real GET does not close the data link on stop** — the close is at
     breakup (`daqDisconnect`) or at the reconnection of the next `configure`. Confirmed in 20190315_patched
     `DaqCtrlNodeI::daqStop` / `disconnect`, v1.12. **It is the CoBo itself that establishes the data link**, and
     the ECC only instructs via Ice. The connection is established at the time of `configure`)
  2. receiver: if an EOF arrives (breakup first, replay, etc.), `EndOfStream` goes to all downstream links.
     **On the normal real-machine path no EOF arrives after ecc stop** (TODO/032 investigation), so the controller
     waits until the earlier of "completion of the natural EOS" or "receive-quiescence of all receivers (the received byte count is unchanged for `eos_quiesce_ms`
     (default **500 ms**, configurable). An unreachable receiver is regarded as quiescent)",
     and **injects the EOS** with the `Stop` command to the receivers (this is the canonical path). `eos_timeout`
     (default **5 seconds**, configurable) is the hard upper limit of both stages. Quiescence detection is a wait to
     drain the in-flight data flushed by ecc stop before folding, and is part of the lossless convention (v1.12)
  3. root-sink: EOS from all sources reached = in-band barrier → TTree finalize + **write run\<N\>_monitor.root** (R10)
  4. Component `Stop` (from upstream), write the run_stop record to JSONL
- **Canonical path for abnormal termination (abort) (v1.6; mechanism corrected to the implementation reality in v1.12)**: an abort too is always
  "closed by flowing an EOS": ecc `stop` (continue even if unreachable) → `Stop` to the receivers (forced EOS) →
  the EOS flows through the chain and root-sink closes the run (incomplete is a visible count) →
  only after that `Stop`/`Reset` of each component.
  **Do not Reset the decoder before the run is closed.** Reason (v1.12 correction): what the cut-off of the Reset sends creates
  is not "a seq gap within the same run" (what is cut off is the trailing batch, and the thread ends with no further sends,
  so the Gap detection of §6.2-5 does not fire). The real harm is **loss of the EOS barrier**:
  root-sink remains with the run open and **fires late as a run_number mismatch fatal on the first Data of the next run
  (exit 6, §6.2-5)**. `Reset` is dedicated to Error recovery after the run is closed.
  **v1.40 (TODO/116)**: the decoder's `Reset` (like the receiver's) **replies after waiting for the sending thread to end** — at the time of the reply the PULL
  bind port has been released, and the final counters (`batches_abandoned` / `eos_abandoned`) are also carried in the reply. Upper limit ≈ poll 100 ms + 2 × `send_timeout_ms`
  (default ≈ 2.1 s < `command_timeout` 5 s). Reason = an Arm right after Resetting a decoder whose sending was jammed by back-pressure failed to bind
  (114 SIGSTOP real-machine test: from Reset to thread end ≈ 900 ms > the Arm budget of 620 ms). `Stop` does not wait (non-destructive; continuing to send under back-pressure is correct).
  This upper limit presupposes **`2 × send_timeout_ms + 0.1 s < command_timeout`** (sndtimeo is a constant 1000 ms that cannot be changed from TOML. If you move it, keep this inequality —
  breaking it makes Reset look unreachable and returns to the 113 situation of "start keeps failing"). While joining, the decoder's REP does not respond, so it appears in `GET /api/status` as a temporary non-arrival (≤ the upper limit)
  (the same for the receiver's Reset. Not silent; a normal appearance during walk-back / stop). **The `*_abandoned` of Reset is only what the thread of that component held in hand**,
  and what was in the ZMQ send/receive queues (undelivered PUSH, unread PULL) cannot be counted from the sender side (114 SIGSTOP real machine: graw 1219 / ROOT 1041 versus `batches_abandoned=1`).
  The actual loss of a run with `eos_closed: false` is **reconciled per run** — the difference between the receiver's `frames` and the root-sink's entries (inprogress file). Per-component partial counters are
  not added up (it would be misread as "counted amount = total loss").
  Exception: only when root-sink itself is dead may the upstream Reset be done unconditionally (an abandon toward an absent downstream is
  counted visibly and harmless).
- **When the EOS did not flow through even when forced (added in v1.12 — termination clause)**: if propagation cannot be observed within `eos_timeout`
  even after the forced EOS, the controller may fold the components without waiting further
  (record `ok: false` and `eos_closed: false` in `run_stop` — §9.2). In this case the run of root-sink
  remains open. **Restart root-sink (or collect its fatal death) before starting the next run**
  — otherwise the first Data of the next run hits the late fatal described above (this is correct detection and is not
  suppressed). run_stop is `ok: false, reason: "abort:..."` or `"error:eos-timeout"`.
- **First run after the zCoBo continued acquiring in the absence of the ECC (v1.46, TODO/110)**: if the stack is brought down without letting the ECC `stop`
  (operational error, power outage, crash — the ECC dies on SIGTERM), **the hw node (getHwServer) keeps running with `isRunning_` still set**.
  When the next run is built from a newly started ECC, `prepare` returns the **registers** of the FW write/read pointers to memStart, but
  the soft copy readPtr on the hw node side remains at the old position X, and the `flushData` right after the new TCP is established by `daqConnect` at the end of `configure` regards "writePtr < readPtr" as a wrap and
  **sends [X, memEnd) as is**. These are the old frames at the head of the run
  (continuation of the previous acquisition = both eventIdx and CoBo time continue from the previous run). The `daqStart()` of `start` is a no-op because of `isRunning_`
  (and no topology frame is emitted either — real-machine `topology_frames=0`), and from then on, through `runInit` → `resetTime`, new frames come from eventIdx 0 / time 0.
  The count is decided by chance by how much fits in [X, memEnd) (measured 19 = 10.6 MB, 91, 17).
  **It cannot be prevented in the controller** (there is no transition by which a `daqStop` reaches the hw node from the new ECC, and an undefined transition is silent. The hw node returns to normal at the
  next regular `stop`. Having a second control path that sends `daqStop` to getHwServer directly via Ice is against KISS and not adopted — user ruling Q3).
  **A regular stop → start does not mix** (112 / 110 run 74 real machine). Handling is decided downstream: **graw is kept** (§7 — lossless, and the real
  DataRouter writes the same byte sequence), **the decoder counts** (§2.3 `acquisition_restarts` / `frames_before_restart` → §9.2
  `run_stop.counters` = the only path that remains in the ledger), **root-sink treats it as an acquisition restart (epoch) and does not discard it as late** (§6.3).
  Primary source = MemRead / DaqCtrlNodeI in reference/20190315_patched (archive/110 Fable ruling).
- The start order (the process launches themselves) is arbitrary (ZMQ connect is retried). The recommended order in the launch script is
  from the bind side: graw-writer → decoder → root-sink → monitor → controller → receivers → ecc-bridge.

### 1.4 Degradation convention under overload (handling the limits of the lossless path)

"The storage path never drops" and "the receiver does not apply back-pressure to the socket" cannot both be satisfied
in a situation where the disk is persistently slower than the input. The convention for that case is fixed as specification:

1. The receive task of the receiver always drains the socket (never-stop). It is separated from the send task by a bounded queue.
2. Lossless links have a finite HWM (default 1000 messages) + a bounded internal queue on the receiving side. Temporary stalls
   (disk spikes etc.) are absorbed by the buffer (default size is at least **2 seconds' worth** of the target rate).
3. If the receiver's internal queue becomes full, that is a **system overload = Error state**. Subsequent frames are
   counted as `overflow_frames` (silence forbidden), the component reports Error, and the controller
   stops the run abnormally and records it in the JSONL. We do not "quietly thin out and continue the run".
4. The monitoring path (PUB from root-sink → monitor) may thin at any time. Drops are detected on the receiving side
   as sequence_number gaps, and the cumulative count is shown in the UI.
5. **Role asymmetry of the response to detected contract violations (made explicit in v1.10, R-P2-6)**: components with a REP
   (receiver / decoder / graw-writer) **report the Error state and continue to drain**, and the controller decides to stop (§1.3).
   root-sink, which has no REP, has **immediate fatal exit** as its only visible declaration of failure, which is more correct than
   silently running on (§6.2-5/6).
6. **The receiver's data link is one at a time (first wins, v1.12)**: an extra connection arriving while a connection is held is
   accepted and closed immediately, counted as `extra_connections` + warned on the first occurrence (not left
   silently stuck in the backlog — silent stall forbidden). **The end (EOF / error) of a connection that carried not a single byte does not
   constitute a run boundary (EOS)** — it is counted as `empty_connections` (prevents the instantaneous end of a stray connection
   from closing the run with a false EOS. The forced EOS path of §1.3 is unchanged). The current connection peer and
   the last receive time (`last_read_unix_ns`) are visible via GetStatus.
   Basis: the real-machine data link is only the single one the CoBo establishes at configure, and the ECC opens no probe
   (TODO/032 investigation). The stock GET DataRouter is also a single connection (it closes the listen itself once established), and
   this convention is the same type with strengthened visibility.

## 2. ZMQ message specification

### 2.1 Serialization method

- **Data plane = MessagePack** (rmp-serde, compact/positional — field names do not go on the wire).
  1 ZMQ message = a single frame. No topic frame (SUB subscribes with an empty prefix).
- **Control plane = JSON** (serde_json). REQ/REP.
- This separation is the same as delila-rs. The decoding on the C++ (root-sink) side reuses the MessagePack reader of delila-rs `tools/delila2root/TDelila.hpp`.

### 2.2 Envelope and Batch

```
Message(enum, fixmap(1) {variant name: payload}):
  Data(Batch)
  EndOfStream { source_id: u32, run_number: u32 }
  Heartbeat   { source_id: u32, run_number: u32, counter: u64 }

Batch(positional array(5)):
  [ source_id: u32,         // unique ID of the sender (table in §3.2)
    run_number: u32,        // ★always carried in every batch
    sequence_number: u64,   // monotonically increasing per source. Reset to 0 at run start
    created_ns: u64,        // send time in unix ns (for latency measurement)
    payload ]               // per link (§2.3)
```

- **Carrying run_number in every batch is an intentional difference from delila-rs** (§14-3). delila-rs carries the run number
  only in commands and EOS and has the consumer latch it, but 2 accidents have been recorded from that
  (stale EOS / loss of EOS leaving root_sink stuck in writing). The extra cost of one u32 removes the latch.
- **EndOfStream is excluded from any thinning or discard rule** (a lesson from a real accident in delila-rs).
- Heartbeat is sent by each source at 1 Hz when idle (for liveness judgment by consumers; not needed while data is arriving).
  **v1.46 (TODO/092)**: **the receiver does not emit a Heartbeat on that link after sending the EOS** (until the send loop is
  recreated by the next `Start`. Data after a reconnection within the same run is passed as before). Downstream closes the run on the EOS, and graw-writer
  **drops the PULL** on the EOS of all expected sources (TODO/117 — released before finalize), so a Heartbeat after the EOS blocked on the `ZMQ_IMMEDIATE`
  PUSH with "peer absent" and was only counted into `messages_abandoned` at a later `Reset` (real-machine log: Heartbeat 1 s after the EOS,
  warn after SNDTIMEO 1 s). No data is lost (all frames and the EOS arrive before the Heartbeat). The decoder keeps emitting Heartbeats to root-sink even after its own
  EOS, but root-sink keeps the PULL open as long as the process is alive, so the same jam
  does not occur (no action needed).
- On lossless links the receiving side **verifies the continuity** of sequence_number, and a gap = a protocol violation,
  Error (§1.4-3). On monitor links a gap is made visible as the drop count.

### 2.3 Per-link payload

| Link | payload | Contents |
|---|---|---|
| receiver → graw-writer | `RawFrames` | `Vec<Bin>` — the byte sequence of MFM frames as is (frame boundary = element boundary) |
| receiver → decoder | `RawFrames` | Same as above (same batch contents. Sent over an independent socket with an independent seq) |
| decoder → root-sink | `Fragments` | `Vec<Fragment>` (§2.4) |
| root-sink → monitor (PUB) | `Snapshot` | §5.3 (histogram) / §5.4 (built event) / status. The format is map-format msgpack (equivalent to `to_vec_named`) and self-describing (not bidirectional between Rust and C++, so ease of evolution takes priority — the same reasoning as EbMessage of delila-rs) |
| each → controller (PUSH) | `LogPost` | A JSON string for one JSONL record (§9. The controller adds ts/seq) |
| slowctl → monitor (PUB) | `Snapshot` | **v1.31**: kind = `slow` — `{kind, ts_ms, samples: [{device, node, param, value, unit, ts_ms, alarm}], counters: {poll_ok, poll_err, parse_err, reconnects, identity_mismatch, influx_points_written, influx_points_dropped, influx_write_errors, influx_last_error}}` (**v1.41**: influx_* belong to the single writer and are 0 / null if there is no `[slowctl.influx]`. A PUB with only the old 5 keys can also be read — `serde(default)`) (map-format msgpack, in the same style as root-sink. Aggregated at 1 Hz, latest values only. The monitor may drop = monitoring path) |

- Batch packing: the receiver closes a batch at the earlier of "8 MiB reached or 10 ms elapsed" (configurable).
  No per-frame ZMQ send / heap allocation in the hot path (CLAUDE.md).
- **Source nature of the decoder (clarified 2026-08-12)**: the decoder sends Fragments as a **single stream** with `source_id = 100` and its own
  sequence_number, and after receiving the EOS of all upstream CoBo and finishing sending the corresponding Fragments it sends **one EOS of its own**.
  The identification of the CoBo is carried by Fragment.cobo. Therefore the
  expected source set of root-sink is only {decoder} (RunState is simplified). graw-writer is directly connected to the receivers, so
  its expected sources remain the configured CoBo set.
- **Detection of decoder acquisition restart (v1.46, TODO/110 — the mechanism of §1.3)**: for each upstream source the decoder holds
  the `max_event_idx` of the current epoch and the `time_floor` (the minimum event_time seen), and judges a restart when a data frame is
  **`event_idx == 0` and `max_event_idx > 8` and `event_time + 100 ms < time_floor`** (v1.47, TODO/134: backward step ≥ 100 ms = `RESTART_MIN_TIME_GAP` 10,000,000 ticks at 10 ns steps. A clock skew between boards (µs) is not a restart)
  (the gate 8 is to exclude the "adjacent mix with backward step 1" of 067 = idx 1 → 0 at the head of a run. The same value as root-sink §6.3).
  Even when judged, **the frame is not dropped and it is not made an Error** (only the epoch of that source is +1 and counted). **v1.48 (TODO/133)**:
  `acquisition_restarts` is **the number of times the minimum over the epochs of all expected sources rose** (an expected source that has not yet come is counted as 0.
  For 1 source it is as before). `frames_before_restart` is **a per-source dictionary `{source_id: n}`** (n = the number of data frames decoded from that source up to the
  time that source first restarted = the number of remaining frames of the previous acquisition. The restart frame itself is not included. Only sources that
  restarted appear, and from the 2nd time on it is not changed. No restart gives `{}`. For 1 source the number is the same as the former total). `info!` once per run.
  The decoder's unit is the receiver, and it has neither the time-band following nor the re-assignment of §6.3 (if a receiver with no old remainder exists,
  the decoder's `acquisition_restarts` may be smaller than the value of root-sink).
  Both are **run counters** carried in the metrics (`GetStatus`), and are not returned by the re-arm (rearm) after sending its own EOS
  (same as malformed — the controller collects `run_stop.counters` after the EOS propagation, so returning them would make them 0.
  Found in 110 real-machine run 73, confirmed in run 76). They return to 0 when recreated at each `Start`. → §9.2 `run_stop.counters`.

### 2.4 Fragment (a decoded frame)

1 CoBo frame (= one AsAd's worth) → 1 Fragment. It carries all the headers from which a GDataFrame (§6.4) can be reconstructed.

```
Fragment(positional array):
  [ event_idx: u32, event_time: u64(48 bits valid), cobo: u8, asad: u8,
    frame_type: u8, revision: u8, read_offset: u16, status: u8,
    mult: [u16;4], window_out: u32, last_cell: [u16;4],
    items: Bin ]   // u32 LE array. 1 item = 1 sample
```

32-bit packing of an item (the bit layout of frameType 1 is the canonical form, and both frameTypes are normalized to it):

| Bits | Contents |
|---|---|
| [31:30] | aget (0–3) |
| [29:23] | chan **raw 0–67** (including FPN. No geometry conversion is done — carried as is in electronics space) |
| [22:14] | bucket (0–511) |
| [13:12] | reserved (0) |
| [11:0] | ADC value (raw, no subtraction) |

- hitPat (36 bytes) is not carried (the RootWriter of the C++ version also does not use fHitPatterns — the raw graw is the reversible backstop).
- The wire cost is about 2× the raw frame (versus 2025 compact), but this is no problem on localhost/LAN,
  and the simplicity of decoding only once, shared by all consumers, is given priority.

### 2.5 Schema drift guard

Follows the approach of delila-rs `src/common/delila_schema.rs`:
- The field order and type tags are declared only once as a constant table in Rust, and a unit test is placed that
  serializes the real struct and matches it against the table (if the table and implementation drift apart the test fails).
- The decoder on the C++ side (root-sink) is forward compatible with the delila approach of "read the first N fields and skip the rest".
- No schema header is put on the ZMQ stream itself (to be considered when it becomes necessary for files).

### 2.6 Command channel (JSON REQ/REP)

- `Command`: `{"Configure": {"run_number": N, "comment": "...", "config": {...}}}` /
  `"Arm"` / `{"Start": {"run_number": N}}` / `"Stop"` / `"Reset"` / `"GetStatus"`
  (JSON representation of a serde enum. Same form as delila-rs `command.rs`).
- `CommandResponse`: `{ "success": bool, "state": "...", "message": "...", "run_number": N|null,
  "metrics": {...}|null }`. metrics is the material for the run_stop record (frames/bytes/drops etc.).
- The REP socket must re-bind on error so that the component does not fall into an uncontrollable state (lesson of delila-rs TODO 58).
- **Direct ZMQ from the UI is forbidden.** Operations always go through the controller's REST (§8.1).

### 3.3 Parameter JSON (v1.32, TODO/078 — the JSON is the authoritative source, the xcfg is a generated product)

- **Do not edit the xcfg directly.** The experiment's canonical xcfg is taken in unmodified as a **template**, and from a `tpcdaq-params/1` JSON (`template` + `knobs` + `exceptions`)
  we generate `configure-<stem>__<first 8 of sha256>.xcfg` and a `prepare-…` with the same content (same JSON → same file). describe is unchanged.
- **Knobs = 12 (15 JSON leaves, v1.36)**; the single definition is `KNOBS` in `src/params/schema.rs` (table and rationale = `docs/PARAMS_KNOBS_ja.md` §7).
  CoBo: `triggerDelay` (10 ns units) / `writingClockFrequency_MHz` / `triggerMode` / `zeroSuppression.enabled` / `pulser.{enabled, voltage_mV, period_ms}` (same value as `Generator.amplitudeStart`, in mV).
  AGET: `globalThreshold` / `peakingTime_ns` (the 16 values of the AGET spec = the xcfg `range`) / `readout` (only `isAllChannelRead`, full/partial) / **`fpnRead` (`isFPNRead`, bool — separated from `readout` in v1.36. The current mini setting is partial + fpnRead true)** (`enableWriteHittedregister` and `channel.Reading` come from the template).
  channel: `lsbThreshold` / `gain` / `triggerInhibition` / `zeroSuppression.threshold`. **All knobs are mandatory** (none may be omitted). Elements outside management leave the template unchanged by even one byte (the round trip is byte-identical).
- **Exceptions list**: `at` is a prefix of (asad, aget, ch), only at the same scope as the knob or coarser. **CompoundConfig's inheritance resolution (`CCfg/View/Search.hpp`) does not
  give a coarse explicit node such as `<AsAd id="1"><Aget id="*">` priority over a uniform value** (it backtracks up a level and re-selects the `*` chain; measured against the oracle, 078 Results section).
  The renderer therefore **expands a coarse `at` into the Cartesian product of the ids that actually exist in the template and writes explicit nodes** (the meaning of the JSON is unchanged; only the generated file gets larger). It is an error if a target id is not in the template.
- **Removal rule**: for a managed knob, all instance nodes of that knob (both `*` and explicit ids) are removed from the template, then the uniform value is written to `*` and the exceptions to explicit ids (omitting the removal lets the template's explicit nodes win — pinned by a negative test).
- **Acceptance**: (1) round trip (no exceptions + template values = byte-identical); (2) the **CompoundConfig oracle** `tools/ccfg_resolve/` (C++11, references the CompoundConfig in reference/ at build time, not committed,
  checks only when env `TPCDAQ_CCFG_RESOLVE_BIN` + `TPCDAQ_XCFG_TEMPLATE` are set, and explicitly states a skip otherwise): all instances match (4,423 on the real template); (3) describe → prepare → configure against a real ECC (new DAQ machine).
- **Id and storage (v1.33, lane B)**: `<id>` = `<template stem (the part without configure-/prepare-)>__<first 8 hex digits of sha256>`, where the sha256 is taken over the **JSON text re-serialized by serde_json (keys in lexicographic order)** (formatting differences do not change the id).
  The JSON goes to `<params_dir>/current.json` (always overwritten) and `<params_dir>/<id>.json`; the generated xcfgs go to `<ecc_config_dir>/configure-<id>.xcfg` and `prepare-<id>.xcfg` (**not written if they already exist**).
  **v1.38 (TODO/113)**: `current.json` is replaced via a temporary file + rename (closing the race in which start reads a non-atomic write), and the phase check, render, and write are done within the same lock section of `run`.
- **REST (v1.33, §8.1)**: `GET /api/params` (404 if none) / `PUT /api/params {token, params}` (400 on validation failure, **409 while Running**, **503** if `ecc_config_dir` is unset; on success render + save + `audit params/put`) /
  `GET /api/params/render?template=…` (dry run, writes nothing). **If current.json exists, run/start uses `<id>` as the config_id for prepare / configure** (describe stays as in the TOML).
  If current.json exists but cannot be rendered, the run is not started (no silent fallback to the TOML). The UI (Parameters view, Exceptions (N) badge, `params <id> · exceptions N` in the status bar) is lane C (to be added to §11 when work starts).
- **Extraction (v1.36, TODO/111)**: `extract(template)` is the inverse of render. Values on the `*` chain → `knobs` (only those that fit the `KnobKind` type and range); values on explicit-id nodes → `exceptions` (`at` is a prefix of the explicit id);
  leaves with no element on the `*` chain → `unset`; elements that exist but are out of type/range, composite knobs that do not map to a single mode, explicit CoBo instances, and explicit ids under `*` → `unsupported {knob, found, why}`.
  **No silent default values** (unset / unsupported are shown by the UI as blank + the reason, with Save disabled). Acceptance = on the real template, extraction → render is byte-identical + re-extraction is idempotent + the oracle.
  REST `GET /api/params/templates` → `{templates: [names of configure-*.xcfg]}` (generated `*__<hash8>` files and other phases are excluded), `GET /api/params/defaults?template=<name>` → the JSON above (400 = name outside the path / invalid, 404 = not found, 503 = `ecc_config_dir` unset).
- **Exceptions list for ZS thresholds (v1.49, TODO/149, 155)**: the per-channel values of `zeroSuppression.threshold` are not written by hand; they are built from a pedestal run (ZS OFF, full, same peaking / gain as physics) →
  `calib pedestal` (table JSON) → `tools/scan/zs_exceptions.py` (threshold = round(mean + k·rms), default k = 5; without `--keep-fpn`, **FPN {11,22,45,56} get threshold 4095 = suppressed**) →
  `tools/scan/zs_params.sh` (composes `zeroSuppression.enabled = true` + the exceptions onto the base JSON, label = peaking). Number of exceptions = number of channels (mini: 272).
  The same table is placed in `[system] ped_table` (§3.2) — consistency comes from the threshold and the downstream subtraction both being derived from the same table.

## 4. Geometry specification

### 4.1 Input = TPCReco `.dat` (both layouts accepted)

- Header lines (any order, `KEY: value`): `ANGLES` (3) / `DIAMOND SIZE` (1) / `REFERENCE POINT` (2) /
  `DRIFT VELOCITY` / `SAMPLING RATE` / `TRIGGER DELAY` / `DRIFT CAGE ACCEPTANCE` (2).
  **Parse and retain all of them, including DRIFT CAGE ACCEPTANCE** (rust_reference drops it).
- Strip lines:
  - **NEW (10 fields)**: `DIR SECTION STRIP COBO ASAD AGET AGET_CH OFF_PAD OFF_STRIP LEN_PADS`
  - **LEGACY (7 fields)**: `DIR STRIP AGET AGET_CH OFF_PAD OFF_STRIP LEN_PADS` (section/cobo/asad = 0)
  - The layout is distinguished by token count (same as TPCReco `GeometryTPC.cpp`). `AGET_CH` is the **signal number 0–63**.
- AUX lines (5 fields): `NAME COBO ASAD AGET AGET_CH` — parsed and registered as Aux (excluded from histograms,
  shown in the waveform view). **The `AGET_CH` of AUX is also the signal number 0–63** (following the column comment
  `AGET_ch[0-63]` of the real ELITPC .dat, settled 2026-08-12), and the same FPN reorder as for strip lines is applied.
- `#` comments and blank lines are ignored. A duplicate `(cobo,asad,aget,ch)` gives a warning + first one wins.
- Real geometry .dat files are not put in the repository. **Tests use synthetic fixtures only** (a reduced mini version and a fictional 2-CoBo version).

### 4.2 Channel key and ChannelRole

- The lookup key is **`(cobo, asad, aget, raw_ch 0–67)`**. rust_reference's 3-tuple (no cobo) is
  a shortcut that assumes a single CoBo, so it is not inherited.
- The implementation is a flat array (a dense index with cumulative AsAd offsets — the same
  idea as TPCReco `Global_raw2normal`). With about 1088 entries there is no reason to use a HashMap.
- The result of a lookup states the role explicitly:

```rust
enum ChannelRole {
    Strip { plane: Plane, section: u8, strip: u16 },  // signal strip
    Fpn { index: u8 },                                 // FPN (1..4)
    Aux { name: ... },                                 // AUX input
    Unmapped,                                          // not listed in the .dat (a warning counter is required)
}
```

FPN is returned as an explicit role, not as a "hash miss" (the same contract as TPCReco's FPN_CH pseudo-strip.
rust_reference drops this information). The occurrence of `Unmapped` is made visible as a count at `info!` or above (no silent handling).

### 4.3 FPN reorder

- FPN = raw {11, 22, 45, 56} (per AGET). For the conversion between signal 0–63 and raw 0–67 we adopt
  rust_reference's 64-element constant table (`REORDER_FROM_GEOMETRY_TO_GRAW`) and apply it **once, at parse time**
  (the hot path is only an array lookup). This table has been confirmed to match TPCReco `Aget_normal2raw` on all 64 inputs.
  A unit test for agreement with both implementations (the loop versions) is provided.

### 4.4 The principle of mm independence

- The DAQ and monitor hot paths use **only the strip number and time bucket** and never convert to mm
  (R5: online **authoritative** reconstruction is out of scope — the QA reconstruction exception is §5.5/v1.25. Histogram axes are also strip/bucket).
- As a result, the mismatch in the strip_pitch convention (TPCReco: `pad_size×1.5` vs rust_reference: `pad_size×√3/2`) needs
  **no decision** in the DAQ layer. Header scalars (ANGLES etc.) are kept as metadata and passed straight through to the UI meta (§10.3) and
  the JSONL (§9). If mm is needed in the future, adopt the TPCReco convention (offline consistency is the reference).
- **(v1.25) The future clause is invoked only for the QA reconstruction module of §5.5 (inside monitor)**. Only that module
  uses mm, with the TPCReco convention. The hot paths of the DAQ, storage, and §5.2 histograms remain strip/bucket only.
- **(v1.43)** The scope of mm use is extended to `src/strip_xy.rs` (distributing the mm of strip segments via `stripGeometry`, once at monitor startup) and
  the UI's Event Display projection (display only, TODO/125). The hot paths of the DAQ, storage, and §5.2 histograms remain strip/bucket only.
  **(v1.45)** The projection computation moved to `src/reco/` (monitor, §5.5). **The UI only packs the points of 0x04 into bins** and does no mm computation (TODO/127).

### 4.5 Agreement test between the two implementations

The geometry parser exists as two implementations: Rust (monitor) and C++ (root-sink, ported from the C++ tpcdaq parser).
Both get a function that "dumps a table of all channels → (role, plane, section, strip) as TSV", and
agreement of the dumps for the same .dat input is verified mechanically in CI (the same idea as the WS conformance test).

## 5. Monitor and histogram specification

### 5.1 The owner of the aggregation = root-sink (decided)

- **Decision**: all R3/R4 histograms are aggregated by root-sink (C++). The monitor (Rust) and the UI are display only.
- Rationale:
  1. **Completeness**: the monitoring-path PUB/SUB is thinned under load. If the aggregation were in the monitor, `run<N>_monitor.root` would be
     "a partial aggregate of only what was seen". root-sink is on the lossless path, so every event passes through it.
  2. **Consistency**: with a single aggregation, the double-bookkeeping risk of "the shape seen in the UI ≠ monitor.root" disappears structurally
     (the same property as the same-object guarantee in §12.7 of the C++ version).
  3. The R10 write-out completes within the same process.
- **Condition (reconciliation with C3 "separation of storage and visualization")**: inside root-sink,
  - histogram fills are done in the thread that processes the builder output (array addition only, O(items)).
  - snapshot serialization and PUB sending are done in a **dedicated thread + double buffer**, sharing no
    lock with the Writer (TTree) thread.
  - At acceptance, confirm by measurement that "storage throughput does not change whether snapshot publishing is stopped or doubled" (§12-8).

### 5.2 Histogram definitions (9 in total + saturation rate)

All are reset at run start, accumulate over all events during the run, and are written to `run<N>_monitor.root` at run stop (R10).
"Pulse height" = the maximum over the time direction of each strip waveform (raw ADC, no subtraction) (the R4 definition).

| id | Name | Type | Bins | Axes | Fill rule |
|---|---|---|---|---|---|
| 1–3 | `StripTime{U,V,W}` | TH2D | Nstrip × 512 | x=strip(1..N), y=bucket | Add all samples with weight=ADC (R3) |
| 4–6 | `Charge{U,V,W}` | TH1D | 512, fixed [0,4096] | x=pulse height | Per event, one entry for the **pulse height of every strip** in the plane (R4①) |
| 7–9 | `ChargeMax{U,V,W}` | TH1D | 512, fixed [0,4096] | x=pulse height | Per event, **one entry for the maximum pulse height** in the plane (R4②) |

- Nstrip comes from the geometry (mini: U72/V92/W92, ELITPC: U132/V225/W226). No hard-coding.
- The x range is fixed at 0–4096. No autorange (the saturation ceiling of 4095 must always be visible — likewise on the UI side).
- Multiple sections with the same strip number are summed into the same bin (stated as a limitation; a per-section view is future work).
- FPN, Aux, and Unmapped channels are not put into the histograms (they do appear in the waveform view).
- **Display orientation (v1.18)**: the UI's 2D displays (StripTime and Event Display) have
  **vertical (Y) = strip, horizontal (X) = time bucket** (the TPCReco convention). The wire (the
  grid of §5.3 / §10.2 = strip is the slow axis) and the TH2D axis definitions of `run<N>_monitor.root` are **unchanged** — the transposition is
  done only in the UI drawing layer.
- **Baseline subtraction in the Event Display (v1.18, display only)**: for each strip of `0x02 Uvw`, the UI
  draws after subtracting from all cells the **mean of the first 25 cells (0..24)** as the baseline.
  **Negative values are kept** (not clipped to 0). The wire stays raw ADC, and this is never applied to the storage path (the FPN pedestal
  algorithm = grawToEventTPC compatible). Reasons: (1) offline analysis recomputes its own
  baseline; (2) "the first 25 samples" is merely a rule-of-thumb hard-coded choice, and
  baking it into the data would take away freedom downstream (ruling by the user, 2026-08-16).
  **The Waveform tab stays raw ADC** (ruled the same day — no need to propose again). The subtraction is not applied to StripTime (Σ ADC accumulation).
- **Unit of pulse-height aggregation (v1.9 clarification)**: per channel assigned to a Strip by the geometry
  (= per physical strip). Charge{U,V,W} gets one entry per such channel, and
  multiple sections with the same strip number enter the same bin as **separate entries**.
  A pulse height is counted only for channels that had one or more samples in that event (a channel with
  zero samples in a partial readout is also excluded from the denominator of the saturation rate). An incomplete event is
  filled with what has arrived (accumulation over all events = R3. Nothing is discarded). Late fragments for an already emitted event are
  not filled (the late_fragments counter of §6.3 makes them visible).
- **Saturation rate (adopted)**: per plane, `number of strips with pulse height ≥ 4095 / total number of strips whose pulse height was counted` (accumulated over the run).
  Not a histogram but 2 counters × 3 planes. Carried in the status (§5.3) and shown in the UI as a %.

### 5.3 Snapshot and status publishing (root-sink PUB)

- Histogram snapshot: all 9 are published at `snapshot_hz` (default 1 Hz). Bin values are carried as f64
  (the wire is the map-format msgpack of §2.3. About 1 MB/s with the W-plane 2D — no problem).
- status (1 Hz, always, even outside a run): `{ run, state, events_built, events_incomplete, late_fragments,
  pending_events, acquisition_restarts, frames_per_cobo, bytes_written, saturation: {U,V,W}, publish_drops }`.
  **`acquisition_restarts` (v1.46, TODO/110)** = the cumulative number of acquisition restarts (§6.3. The 12th key, after `pending_events`).
  **`sources_behind` (v1.48, TODO/133)** = the number of expected sources whose generation remains at the minimum (0 if all sources are at the same generation. The 13th key,
  after `acquisition_restarts`. A dead AsAd becomes visible).
  The monitor (Rust) `StatusPayload` currently skips over these keys (unknown keys are tolerated) — showing
  `restarts N` in the UI status bar comes later (110 lane C, deferred by the user's default).
  `events_built` = the total number of emitted events (complete + incomplete). `publish_drops` =
  the number of built events thinned (distinct from the "monitor drop count" of §5.4 — this one is the sender's intentional thinning).
  `pending_events` (v1.10, R-P2-5) = the instantaneous value of events being assembled by the builder. Since the upper bound of pending memory is
  proportional to rate × build_timeout, it is always made visible, and the implementation emits a
  warn once when a warning threshold (constant 1000) is exceeded (no hard limit is set, because it would conflict with the lossless contract).
- Latest built event: published at up to `event_publish_hz` (default 20), **latest first** (including the raw waveforms of all strips
  = the same payload as the waveform view R13). The event ID (run / event_idx) is mandatory (R9).
- **Wire format (v1.9 settled)**: the envelope has the same form as §2.2
  (`{"Data": [source_id=101, run_number, sequence_number, created_ns, payload]}`).
  sequence_number is **monotonically increasing with no reset per run** (an exception to the zero-reset rule of §2.2 —
  the monitor link's only purpose is making gaps = the number of drops visible). The payload is map-format msgpack
  (self-describing, equivalent to `to_vec_named`), and the `kind` key distinguishes 3 kinds:

  | kind | Content |
  |---|---|
  | `"status"` | The status fields above, as a map as they are. `state` is a string, `frames_per_cobo` is `{cobo (decimal string): u64}`, and `saturation` is `{"U": {"saturated": u64, "counted": u64}, "V": …, "W": …}` |
  | `"hist_snapshot"` | `{ kind, run: u32, hists: [ { id: u8(1..9), name: str, nx: u32, ny: u32(1 for 1D), bins: Bin } ×9 ] }`. `bins` = raw f64 LE bytes (length nx*ny*8). The 2D index = `(strip-1)*512 + bucket` (strip is the slow axis), the 1D index = bin number 0..511. No under/overflow bins (ADC 0..4095, bucket 0..511, and strip 1..N are structurally within range) |
  | `"built_event"` | `{ kind, run: u32, event_idx: u32, complete: bool, fragments: [ the Fragment positional array of §2.4, … ] }` (fragment order = (cobo,asad) ascending = §6.3 v1.3) |

### 5.5 Online QA reconstruction (v1.25 — partial revision of R5)

**Decision (Fable 2026-09-02, originating from a user proposal)**: given the expectation that the production experiment is
alpha-only (1 event = 1 track), a **sampling track reconstruction (QA reconstruction) restricted to the monitoring path**
is brought into scope. R5 "online reconstruction is out of scope" is **maintained for the authoritative reconstruction** — the authoritative
TrackTree belongs to the offline analysis (minitpc-analysis, in the Higs-side repository), and the DAQ does QA display only.

- **Purpose**: display the four electric-field-scan metrics (v_drift = z endpoints / diffusion = width vs z / attachment = charge vs z /
  gain = charge/length) live during a run, turning condition tuning from "analysis the next day" into
  "work done on the spot" (the mini eTPC commissioning is the direct driving requirement).
- **Placement = a pure-function module inside the monitor (Rust). It does not go into root-sink.**
  The reason §5.1 puts the histogram aggregation in root-sink is completeness (accumulation over all events), whereas QA reconstruction is
  satisfied by statistics and does not require completeness → C3 "separation of storage and visualization" takes priority.
- **Input = the existing built_event PUB (§5.3, `event_publish_hz` default 20 Hz, latest first)**.
  No new wiring. Losses are already made visible by the existing sequence gaps. 20 Hz × 1 h ≈ 72,000 tracks is
  enough for QA statistics.
- ~~Algorithm = a Rust port of minitpc simplefit, the Python implementation is authoritative~~ → **(v1.45) Algorithm = a port of the user's analysis macros
  `macros/analyzeUVW.C` + `macros/makeTracks.C`, the real macros are authoritative** (the dual-implementation pattern of §4.5 = the C++/ROOT side is the macros.
  Cross-check = `tools/macro_oracle/` runs the real macros to produce JSON, compared by `tests/reco_macro_oracle.rs` (env-gated), agreeing on the 201 events of run70).
  The implementation is **`src/reco/`** (a pure-function module inside the monitor, from the same section-summed grid as 0x02, only for the events that make 0x02 — 1 event ≈ 0.22 ms).
  The result is **0x04 Track** (§10.2). We do not add a configuration value for the one-track hypothesis — the `tracks` of 0x04 is made a list so as not to structurally exclude multi-branch events.
  TODO/074 (simplefit) is superseded (only the QA histogram id 20s part remains, after multiple tracks).
- **Constraints**:
  1. **The one-track hypothesis is a configuration value** (e.g. `hypothesis = "single_alpha"`). Hard-coding it is forbidden
     (an invariant on par with the channel count. ELITPC includes multi-branch events — rejecting such events is acceptable, but
     a design that structurally excludes multi-branch events is not).
  2. **A hypothesis violation is rejected + counted + shown in the status** (multiple blobs / fewer than 3 z slices /
     residual RMS above threshold). No silent handling.
  3. **Head/tail estimation is not implemented** — in measurements every method gives ~50 % (at 100 mbar the alpha
     does not stop and there is no Bragg peak, so it is undecidable in principle). The direction is decided offline using
     prior information about the source position.
  4. **The mm conversion is confined to this module**, with the TPCReco convention (the future clause of §4.4 is invoked).
  5. Baseline: built_event is raw ADC (R13). The reco baseline = the **mean of cells 1..20 of the grid**
     (`PED_LO..=PED_HI` in `src/reco/mod.rs`, same as the macros). **v1.49**: for ZS data the same formula is applied to the restored grid of §5.4
     (missing cells = the table's round(mean)), so with a table the hits are the same as for non-ZS data.
     Not applied to the storage path or the §5.2 histograms (the v1.18 ruling is maintained).
- **Output**: QA aggregates go to the **id 20s** of WS 0x10/0x11 (a separate space from the id 1–9 of §5.2 = root-sink
  accumulation over all events. The UI states "sampled" explicitly). A track-overlay type (0x04) will be ticketed when needed.
- **run.root is unchanged** (the grawToEventTPC-compatible drop-in equivalence of §6.4 is inviolable. A friend tree is not allowed either).
  **No QA histograms go into `run<N>_monitor.root` either** (preserving the all-events-accumulation-only principle. If
  persisting sampled aggregates becomes desirable, rule on it separately via the JSONL run summary (§9)).
- **Acceptance**: confirm by measurement that, with reco on/off, the storage throughput (§12-8) and the WS delivery (drops, latency) are
  unchanged. No preliminary spike is needed (even Python's measured 3.7 ms/event at 20 Hz sampling is ~7 % of a core — it cannot become the bottleneck).

### 6.2 Lossless-conversion checklist (acceptance items for the implementation unit)

1. `ZMQ_SUB` → `ZMQ_PULL`, remove SUBSCRIBE. The sink side binds.
2. Make RCVHWM **finite** (with HWM=0 no back-pressure arises — this is the crux).
3. Make the internal Channels (receive → builder → Writer) bounded (the implementation where push blocks when cap>0 already exists).
4. Only the monitor tee (to the Publisher) stays bounded and droppable (it does not take part in back-pressure). Drops are counted.
5. Add a sequence_number continuity check (currently explicitly skipped). A gap = Error.
   **v1.10 extension (R-P2-1)**: a run_number mismatch within a run (for both Data and EOS) is also a
   **fatal (exit 6)** of equal rank. The former "counter only" behaviour left a path by which a mixed run
   could turn into a file bearing a completed run's name. A stale EOS while idle (counted and ignored) and
   an unexpected source_id (counted, not mixed in) remain non-fatal as before.
6. Malformed batch: warn+skip → **stop with Error** (under the lossless contract nothing is silently discarded).
7. Make explicit (assert) the places where a push to a closed channel is a silent discard.
8. No blocking external IO at a run boundary (RunOpen/RunClose).

### 6.3 Event builder (new, eventIdx-based)

- Expected fragment set = the set of `{(cobo, asad)}` derived from the configuration + geometry (mini: {(0,0)},
  ELITPC: **{(0,0),(0,1),(0,2),(0,3)}** (confirmed on real data in v1.7 — 1 logical CoBo × 4 AsAd).
  Follows the actual layout in the .dat).
- Key = `(run_number, event_idx)`. An event is complete when all expected fragments have arrived; when
  `build_timeout_ms` (wall clock, default 1000 ms) is exceeded it is **emitted with an incomplete flag** (not discarded).
- Emission is in ascending event_idx. **The TTree has 1 entry = 1 built event (PEventTPC, v1.8)** —
  the structural avoidance of the current GET problem "concatenation in arrival order scrambles the order" (PROPOSAL Q3) is achieved here.
- **The fragment order within an event is made deterministic by ascending (cobo, asad)** (v1.3. Arrival order
  wiggles from run to run, so this keeps the 2-source build match and the TTree comparison of §12-4 from giving false negatives due to ordering).
- **Independence from arrival order is backed by real data (v1.23, TODO/067)**: in a real pedestal run
  (467 events) we measured 2 rotations of the AsAd arrival order (`2,3,0,1` etc.), **40 eventIdx regressions
  (the regression width is always 1 = only adjacent events are interleaved)**, and a maximum arrival span of 6 frames for one event.
  The builder **must depend neither on AsAd order nor on eventIdx monotonicity** (the current eventIdx
  grouping implementation satisfies this. Arrival span 6 ≪ build_timeout).
  **Addendum of the same day (full scan of all runs, TODO/068)**: even in the single-file format (via GetController),
  there are 25,438 places in 36 pedestal runs where events are not contiguous blocks — but **the interleaving is always
  by one adjacent event** and eventIdx is monotonic (0 places in pulser/physics = rate-dependent). No fixed depth of a reordering
  "window" is provided (the current eventIdx key + build_timeout scheme is the right one, and is sufficient for the measured upper bound of
  1 event). **Incomplete events caused by truncation at the end of a run** (15 in all the data,
  with the AsAd drop-out order 3→0→1→2 being regular = caused by the run stop on the source side) are handled by the default
  "emit with incomplete flag (not discarded)" as is — ruled that no additional policy is needed.
- **Handling of late arrivals (after emit) (revised in v1.8)**: PEventTPC is written out in full as one entry per eventId
  (same semantics as the eventId de-duplication of grawToEventTPC), so a late
  fragment for an already emitted event is **not written to the TTree; it is counted as `late_fragments` + made visible with a warn**.
  The data itself is always in the raw graw (the lossless storage path) — from v1.8 run.root is a "converted output for analysis"
  (including FPN dropping, window cutting, and pedestal subtraction) and is not what carries the lossless guarantee.
  (The old note about the GDataFrame test mode was removed with the removal of that mode in v1.17.)
- **Duplicate fragments (the same (cobo,asad) within the same event, made explicit in v1.10 — R-P2-4)**:
  counted in `duplicate_fragments`, and then **all of them are put into the event and all are filled (added)** —
  "do not discard" takes priority. Duplicates are not expected to occur on the real machine, and the resulting
  double accumulation in PEventTPC's chargeMap / the monitor histograms is visible through the counter. Revisit if a difference from the real-machine oracle is observed.
- **Acquisition restart (v1.46, TODO/110 — mechanism in §1.3)**: when eventIdx returns to 0 in the middle of a run
  (a new acquisition starts after the leftover frames of the previous acquisition), this is not discarded as late ("an eventIdx older than the emitted ones") but is handled as a
  **switch of the in-run generation (epoch, starting at 0)**.
  - **Per-source epoch (v1.48, TODO/133 — closes the hole where the original incident recurs with the AsAd-major send order of the 4 AsAd (primary source `MemRead::flushData`))**:
    Each (cobo, asad) holds `{epoch, max_seen, time_floor}`. The **decision (made before the late decision)** uses **that source's** values:
    `event_idx == 0` and `max_seen > 8` and `event_time + 100 ms < time_floor` (`kRestartMinTimeGap` = 10,000,000 ticks,
    the same value as the decoder — v1.47, TODO/134). When it holds, that source's epoch is incremented by 1 and `source_restarts` by 1. The v1.46
    condition "complete or already emitted" is removed (this also catches the §1 oversight = the case where the old head is entirely incomplete). The "adjacent
    interleaving with regression width 1" of 067 has idx ≤ 8, so it does not fire.
  - **Key = `(run, source epoch, event_idx)`**: a fragment goes into the pending set of that source's current epoch (so the old leftovers of other AsAd are not mixed
    with the new idx 0). The high-water mark for the late decision (`emitted_upto`) and the interval list of emitted numbers are **per epoch**. Emission is
    ascending within an epoch, and head-of-line waiting is per (run, epoch).
  - **Following by time band**: each epoch holds the time band `[floor(e), ceil(e)]` of the fragments that entered it. For a
    fragment of source s (epoch e_s), if the maximum epoch in the run e_max > e_s and `floor(e_max) ≤ event_time + 100 ms` and
    `event_time ≤ ceil(e_max) + 100 ms` (both ends inclusive), then regardless of idx s is advanced to e_max and counted in `source_epoch_joins`
    (not counted in `source_restarts`). The upper bound is needed because the clock restarts near 0 at a restart, so the times of the old leftovers are
    **larger** than those of the new epoch. This closes the miss for an AsAd that has no old leftovers (it starts from idx 0 with new times). It does not fire for a single source.
  - **Re-attachment at restart detection**: at the moment source s advances from epoch e to e+1 (before closing the run's epoch), fragments that satisfy all of the following 4 conditions
    are moved to the pending set of the same idx in epoch e+1: ① it is in the pending set of epoch e and belongs to **another source s′ that is still in epoch e**
    (the epoch-e fragments of a source that restarted earlier are exactly the old leftovers); ② `event_time + 100 ms < floor_old(s)` (floor_old =
    the minimum event_time of s's old epoch = the start of the old leftovers); ③ `event_time < t0 + (floor_old(s) − t0) / 2` (no equality; t0 = the event_time of the frame at which the restart was
    detected. The new acquisition clusters near t0 and the old leftovers cluster just before floor_old, so the midpoint separates them — this keeps it from pulling in the long old leftovers of a dead
    AsAd); ④ the destination epoch has not yet emitted that idx or above. After the move, s′ is advanced to e+1 and counted in
    `source_epoch_joins`, the emptied events of the old epoch are erased, and the time band of epoch e+1 is updated. This is for the case where an AsAd with no old leftovers comes **before**
    the first restart in AsAd order (there is no new epoch yet, so following cannot pick it up). It does not fire for a single source.
  - **Run epoch = the minimum of the epochs of all sources in the expected set** (expected sources that have not yet arrived count as 0). Each time this rises (it can rise by 2 or
    more through following): the pending set of the old epoch is pushed out in ascending order (as complete / incomplete — not discarded.
    `take_restart_flush()`) → the old epoch's emit count is added to `events_before_restart` → `acquisition_restarts` +1. Until then, the
    old epoch's pending events are emitted when they become complete or at build timeout. stderr gets one line per run.
  - **Dead source** (an AsAd that stops coming without restarting): the run's epoch does not rise. Events of the new epoch are emitted at timeout as incomplete
    and do not become late. It is visible in `sources_behind` of the status PUB (§5.3).
  - **Same numbers in the new epoch are counted, not written (user ruling Q1, 2026-10-13)**: an eventId is unique within a run
    (TPCReco's eventIdMap, same semantics as the recorder's `admit`), so if the number of an event about to be emitted in the new epoch has
    **already been emitted by another epoch** (v1.48: in either direction — including when the old epoch emits later by timeout),
    both complete and incomplete events are **not emitted and `restart_duplicates` is incremented by 1** (the high-water mark is advanced).
    The decision is made in **one place, the event builder**, so that PEventTPC, the raw tree (§6.7 — it is written after the builder has removed them, so unchanged), and the
    contents of the monitor all agree. Only the K events with the same number as the previous epoch are dropped (carrying the high-water mark over as is would drop the whole new acquisition
    = the same loss as the original incident of 110). The data itself is always in the raw graw.
  - The recorder (`root_recorder.hpp`) resets the eventId high-water mark (`last_event_id_`) when `BuiltEvent.epoch` changes.
    Emitted numbers are held as an **interval list** (emission within an epoch is ascending, so a single interval if there are no gaps) and are released at run close
    (so RSS does not grow in the resident process).
  - **Never silent**: the close line is always `root_sink: run N closed (batches= events_complete= events_incomplete=
    late_fragments= restarts= events_before_restart= restart_duplicates=)` (`rs_core.hpp`, per-run difference). The final JSON has
    `acquisition_restarts` / `events_before_restart` (the number emitted in old epochs, cumulative) / `restart_duplicates`. The status PUB has
    `acquisition_restarts` (§5.3).
  - **Acceptance**: with a synthetic sequence (19 old events 2038..2056 → new 0..2060), `late_fragments=0 / restarts=1 /
    events_before_restart=19 / restart_duplicates=19`, the entries of both PEventTPC and the raw tree are 2061, and
    `duplicate_event_ids=0`. On the real machine (ELI-NP mini, 2026-10-13): run 73 = 91 old events → `late_fragments=0 restarts=1
    events_before_restart=91 restart_duplicates=39` (= 91 + new 298 − duplicates 39 = 350 complete), run 76 = 17 old events, 0 duplicates
    (the new run did not reach the numbers of the old head). The original incident (run 29) discarded 2,057 events as late in the same situation.
- With a single-CoBo configuration it is effectively a pass-through (the expected set has 1 element). Multi-source verification uses two graw_replay instances running in parallel (§12-4).

### 6.4 TTree (PEventTPC / TPCReco compatible — fully revised in v1.8)

**Decision (v1.8, user ruling)**: the event format of run.root = **identical to the output of TPCReco `grawToEventTPC`**.
Offline analysis is TPCReco (common to mini/ELITPC), and the value lies in being able to use our output for analysis
as is, without a conversion step. The GDataFrame output up to v1.7 was ruled a flaw.

**Redefinition of positioning (v1.19, user ruling 2026-08-16 — originating from Wojciech's request)**:
**The only raw data is graw**. ROOT is not "another format of the raw data" but an
**analysis-ready product for starting analysis right away**, and may include processing (the safety net is that it can in principle be rebuilt from graw;
indeed PEventTPC is already pedestal-subtracted and thus already in this positioning).
- **Parallel writing (v1.21, TODO/064)**: `--recorder-workers N` (default 1). **N=1 is exactly the same as
  before** (code path and output names). With N>1 each worker owns a full set of TTrees exclusively and
  distribution is round-robin (bounded queues, back-pressure, lossless). Within a worker eventIdx is monotonic;
  a total order across files is not guaranteed (events are self-contained; comparison is by content match keyed on eventId).
  Measured: mini N=4 = 152 events/s (isolated) / 100.4 events/s (30 min sustained @224 Mbps).
- **The base is, as before, the grawToEventTPC-compatible PEventTPC** (the content-match oracle of §12-3 is unchanged).
- In the future, processed derivatives such as **Unfolding (per-strip signal restoration) and per-strip gain normalization**
  may be **added** (WARSAW_PLAN §7. The default form is an addition that does not break the base-compatible tree —
  the concrete form will be defined by revising this section at implementation time).

- **Tree/branch (the form that TPCReco EventSourceROOT hard-expects)**: tree name `TPCData`
  (empty title), a single branch `Branch("Event", &pevent, 128000, 2)` (splitlevel 2).
  **1 entry = 1 event (all AsAd built)**. Origin = `ConvertGrawFile.cpp:40-45` +
  `EventSourceROOT.cpp:25/74` (HIGS2026_online, confirmed against the real source 2026-08-13).
- **Classes**: `PEventTPC` + `eventraw::EventInfo` (from TPCReco). **TPCReco has no license
  specified (= all rights reserved), so no copy is committed to the repo** — the same
  **build-time reference** scheme as the .ice of 017: the headers under `TPCDAQ_TPCRECO_DIR` (default `reference/TPCReco/TPCReco-HIGS2026_online`)
  are included, and a rootcling dictionary is generated with our LinkDef (pragma: PEventTPC+ / eventraw::EventInfo+ /
  same::global_properties+ / nestedclasses). The dependencies close over 6 files
  (PEventTPC.h/.cpp, EventInfo.h (whether .cpp is needed is decided at implementation time), StripTPC.h (GeometryTPC is only forward-declared),
  CoBoClock.h (boost headers only)). If redistribution permission from Warsaw is obtained, promote to third_party/tpcreco.
  **The streamer checksum match is fixed in the acceptance test** (measured: PEventTPC v1 0xf71c32cf /
  eventraw::EventInfo v1 0xfea093e4 / global_properties v1 0x49e6428c — copy source fixed to
  HIGS2026_online. Mixing in other snapshots in which myChargeArray came and went breaks the match).
- **chargeMap key** = `{dir(U=0/V=1/W=2), section(0="-"/1=A/2=B), number(1-based), cell(0..511)}`,
  and the value is the **`+=` accumulation** of `AddValByStrip` (use the tuple setter — equivalent to the shared_ptr<StripTPC> version).
- **The myChargeArray branch is disabled by default** (`SetBranchStatus("TPCData.myChargeArray*", false)` —
  the same as the production default `disabledBranches=["TPCData.myChargeArray*"]`. Saves float[3][3][256][512] ≈
  4.7 MB/event. It remains in the streamer, so class compatibility is unaffected).
- **Fill semantics (`EventSourceGRAW::fillEventFromFrame` = identical to the HIGS2026_online implementation)**:
  - Scan **normal ch (0..63) only** (FPN reorder via `Aget_normal2raw`). FPN and non-strip ch are
    dropped (losslessness is carried by the raw graw — no contradiction with the absolute rule: this is the "converted output").
  - strip = geometry lookup (geo.hpp, 018). `AddValByStrip(strip, cell, value)` into
    the chargeMap (key = tuple<int,int,int,int>).
  - **signal window**: cells outside cell ∈ [minSignalCell, maxSignalCell] (default 5..506) are dropped.
  - **Pedestal subtraction (default ON)**: the same algorithm as TPCReco `PedestalCalculator(GRAW)` —
    ① average the 4 FPN ch per cell (for the pedestal window 5..25 and the signal window respectively)
    ② in the pedestal window of the normal ch, average `raw − FPN average` per channel (= offset;
    pure arithmetic equivalent to the integer centres of the 256 bins of a TProfile)
    ③ correction = offset + FPN_ave_signal[cell], stored value = raw − correction.
    Reset and recomputed for every (cobo,asad) frame (self-contained within the event, no run state).
  - **ZS table mode (v1.49, TODO/151)**: when the above algorithm is applied to zCoBo ZS data (samples below threshold **do not exist**, FPN ch also suppressed),
    there are almost no samples in the pedestal window, so the offset ≈ 0 and the FPN term is 0, and the chargeMap remains raw ADC (149 run 133.
    **grawToEventTPC breaks in the same way** — WARSAW_PLAN §7). So, only for **frames that look ZS**, the mean of `--pedestal-table` (the table of §3.2) is subtracted:
    * **Predicate** (`frame_is_zero_suppressed`): among the ch that have at least one sample (raw 4 × 68 including FPN), those whose number of samples in the pedestal window
      [min_pedestal_cell, max_pedestal_cell] (default 5..25 = 21 cells) is less than the window width are a **majority** (exactly half is not included).
      full / partial (non-ZS) read all cells of the ch they read, so it is false; ZS has almost no pre-trigger samples, so it is true.
    * **Subtraction in table mode**: correction = table mean (asad, aget, raw ch), **no FPN term**, signal window unchanged, **only existing samples** get `adc − mean`
      (missing samples are not filled — the chargeMap stays sparse). `pedestalSubtracted` is true. Channels absent from the table are counted, not written.
    * **No table**: the conventional algorithm as is (= raw ADC remains), counted, with a **WARN once per run**. Storage is not stopped (graw is the safety net, absolute rule).
    * **Non-ZS frames use exactly the conventional algorithm even if a table exists** (same code path) → **the grawToEventTPC match oracle of §12-3 is unchanged whether or not a table exists**
      (151: 0 differences on 3 real graw pairs). With `--pedestal-remove 0` neither the predicate nor the table is used.
    * **Property**: the chargeMap in table mode retains only samples at or above threshold (only positive outliers. Negative fluctuations and the sub-threshold tail are lost).
      Measured (156, per-channel mean + 5σ): total charge −3 %; the number of hit channels, track length, σ_z, and σ_2D are the same as non-ZS (SCANS S18).
    * Counters `pevent_zs_frames_table` / `pevent_zs_frames_no_table` / `pevent_table_missing_channels` (final JSON.
      The per-run path = close line / status / run_stop is TODO/159).
  - **EventInfo**: eventId = eventIdx, timestamp = eventTime,
    runId = **`%Y%m%d%H%M%S` of the run start TS** (the same derivation as TPCReco `RunIdParser` —
    the substitute for the v1.7 §6.4 "do not carry run_number" exists here naturally),
    pedestalSubtracted = subtraction flag.
    **Implementation note (020)**: the wire carries no run start time, so runId is generated by root-sink from the
    local time at the moment it opens the run. It may differ by a few seconds from the TS in the graw file name (the local time that graw-writer takes independently); the
    authoritative source for the correspondence is the logbook (§9). In P4 the controller will put the official run TS in the
    Start command and unify it across all components (design input of 016).
- **Settings** (config `[root_sink]` → CLI): `pedestal_remove` (default true) /
  `min_pedestal_cell` 5 / `max_pedestal_cell` 25 / `min_signal_cell` 5 /
  `max_signal_cell` 506 (the same values as the defaults of TPCReco `allowedOptions.json`).
- Compression is **101 (ZLIB-1) by default and configurable** (v1.5. Directly confirmed with a real 2026 file that the real-machine grawToEventTPC output is
  ZLIB level 1 — WARSAW_PLAN §4).
- **Treatment of GDataFrame (demoted in v1.8 → fully removed in v1.17)**: **user ruling (2026-08-15):
  GDataFrame is the format of graw2root (a separate tool bundled with GET) and is entirely unnecessary in our chain.**
  The removal condition set in v1.8, "once the same-run real-data oracle for PEventTPC closes", has been **met** by 021
  (`compared 3852 events, 0 differences`). Therefore:
  ① remove the intermediate representation (Fragment → GDataFrame → PEventTPC) so that the **Filler reads Fragment directly**
  (equivalence is guaranteed not by sharing an intermediate representation but by **the content-match oracle of §12-3**)
  ② remove the `--format gdataframe` test-only mode and its dedicated regression
  ③ tidy up the GDataFrame-family classes in third_party/get that are no longer needed. Implementation = TODO/054.

### 6.5 File naming and lifecycle

- **worker parts (v1.21)**: when `--recorder-workers` N>1, worker k's output is
  `run{run:04}_w{k}.root` + rotation `run{run:04}_w{k}_{part:04}.root`
  (the 1 GiB rotation is independent per worker). N=1 keeps the conventional naming.

| Output | Name | Notes |
|---|---|---|
| Event TTree | `run{run:04}.root` (`_0001` appended on rollover) | While being written it is `run_inprogress_<unixtime>.root`, renamed at finalize. On abnormal termination it stays as inprogress (it does not turn into a complete run) |
| Monitor histograms | `run{run:04}_monitor.root` | Written after EOS from all sources. **Within 10 seconds of EOS** (a numeric form of R10 "promptly") |
| raw tree (optional) | `run{run:04}_raw.root` | v1.26 §6.7. Default off. While being written it is `run_raw_inprogress_<unixtime>.root`, renamed at finalize, and on abnormal termination it stays as inprogress (the rules are the same as for the event TTree; only the namespace is separate). **No rollover** (v1.28) |
| Raw graw | `CoBo{K}_AsAd{A}_{TS}_{idx:04}.graw` | **Exactly matches the real-machine DataRouter naming** (§7). It does not contain the run number — the correspondence is held by the directory and the logbook |
| Non-AsAd control frames | `ctrl/CoBo{K}_{TS}_{idx:04}.graw` | v1.2. A subdirectory under the run directory (invisible to the offline glob). §7 |

Output location: a per-run directory `<output_root>/run{run:04}/` is created and all outputs are gathered in it.

- The correspondence between run number and the real-machine graw naming is **held by the run directory and the JSONL logbook (the file-record entries of §9)**
  (compensating for the graw names not containing the run number. The management unit of logs, UI, and operations is always the run number).
- **A run with 0 events creates no ROOT file** (made explicit in the 011 review — lazy open.
  The record "there was a run but with 0 events" is held by the logbook and the counters. No empty TTree file is left behind).
- The event TTree is ideally **a single per-run file with all CoBo/AsAd merged** (user confirmation 2026-08-13.
  Rollover is for size protection only). If the offline side requests graw-like naming for ROOT too, it is handled
  **with symbolic links** (no renaming or duplication. An operating procedure, not a deliverable).

### 6.7 raw tree output (v1.26 — direct connection to the mini analysis chain, optional)

**Decision (Fable 2026-09-03, originating from a user request)**: to connect the standalone analysis chain of the mini eTPC
(`macros/` — graw2root.C → analyzeUVW.C → makeTracks.C; plain ROOT only, no TPCReco needed) to the DAQ
**with no change downstream**, root-sink gets an **optional second output**
`run{run:04}_raw.root`. When enabled, graw2root.C (the conversion step from raw .graw to ROOT) becomes
unnecessary.

- **Format = the same contract as the output of macros/graw2root.C** (= the input contract of the downstream analyzeUVW.C):
  TTree `raw` (1 entry = 1 built event, entry order = emit order = ascending event_idx §6.3)
  - `eventId/i` = the builder's event_idx (= the frame header eventIdx)
  - `eventTime/l` = the 48-bit CoBo timestamp of the first fragment of the event (the first in ascending (cobo,asad))
  - `adc[4][68][512]/S` = **raw ADC (including FPN, no subtraction — raw values, same as R13)**.
    The leaf list is **generated at startup from the number of elements nAsad of the expected fragment set (§6.3 `--expect`)**
    (`adc[{4×nAsad}][68][512]/S` — no hard-coding. mini = the 1 element `0:0`, exactly matching the macros contract.
    v1.28: the old "observed number of AsAd" is withdrawn — the branch is needed before the first event, and
    the array must not shrink even if the first event is incomplete). The order of the AsAd blocks = the rank in ascending (cobo,asad) of the expected set.
    **A (cobo,asad) outside the expected set is counted, not written** (`raw_unexpected_fragments`). Items with chan ≥ 68
    likewise (`raw_items_out_of_range`, the same defence as the Filler).
- **Default off, on by setting** (on is expected in the mini profile. CLI `--raw-tree`, TOML `raw_tree`).
  **PEventTPC (§6.4) is unchanged** — an addition, not a replacement. It does not touch the grawToEventTPC-compatibility oracle (§12-3).
  **Independent of `--no-root`** (v1.28): `--no-root --raw-tree` = raw only (no geometry needed —
  the minimal form for mini operation that uses only the macros chain).
- Treated as a **storage path** (intentional dropping is forbidden. Failure of open / mkdir is the same
  `fatal_reason` → exit 5 as for PEventTPC = it does not keep running unable to write, silently. Counters are `raw_*` in the final JSON).
  An incomplete event is filled with what arrived, and the missing parts are 0 (the same semantics as the memset default of graw2root.C).
  **The raw tree stays zero-padded even for ZS data** (v1.49 — keeps the raw ADC contract. Suppressed cells and missing ones are not distinguished). The macros'
  ped (average of cells 1..20) breaks on ZS raw, so the bridge = `tools/scan/zs_restore.C` (a **same-name file**
  `OUT_DIR/zsfilled/runNNNN_raw.root` with the suppressed cells (0) filled with the table's round(mean), `metrics_for_run.sh --zs-fill`, TODO/154). The same name is required because the macros
  build the output name by the substitution `_raw.root → _uvw.root`. It is not put into root-sink (the storage path stays raw; restoration is a product of the analysis side).
  Writing is by a **single writer = a dedicated thread + bounded queue (in-band RunClose)** (the mini rate
  ≈ 28 MB/s @100 Hz is fine for 1 thread. It is not put on worker splitting (§6.5) — downstream assumes a single file.
  **No rollover either** (v1.28, same reason. A 10-minute run @100 Hz ≈ 16 GB uncompressed — ROOT has no problem with a
  single file). It shares neither locks nor queues with the PEventTPC recorder thread
  (same practice as §5.1). The cost when enabled is only one copy of BuiltEvent in the aggregation thread.
- **Why root-sink**: PEventTPC is pedestal-subtracted and geometry-applied and **cannot restore the raw ADC**
  (the route of "adapting" graw2root.C to read PEventTPC fails in principle).
  Only root-sink holds the raw waveforms and the built events at the same time.
- **Acceptance (oracle = graw2root.C itself)**: for the same mini run, root-sink's
  `run{N}_raw.root` and the tree `raw` of graw2root.C (same .graw) **match on all entries**
  (eventId / eventTime / all adc elements — comparator `tools/root_sink/compare_raw`, with a negative control).
  Oracle input = the real 2025 mini .graw (`TPCDAQ_REAL_GRAW`, compact — graw2root.C was made
  frameType 2 capable on 2026-09-14. **The 2026 pulser is a single file of the ELITPC 4 AsAd, so it does not match
  graw2root.C's 1 frame = 1 entry and cannot be used as an oracle**).
  In addition the variation of §12-8 (PEventTPC write throughput unchanged within ±5% with raw output on/off).
- **Implemented and measured (2026-09-14, the Results section of TODO/075 is authoritative)**: on a real 2025 mini run, against graw2root.C
  `compared 108 events, 0 differences` (negative control: 1 difference). §12-8 variation: with N=4, at both 224 Mbps /
  672 Mbps the raw on/off difference is +0.3% / +0.2% (lossless counters all 0). The raw file is 192 KB/event
  (pulser, ZLIB-1) = 19 MB/s at 100 Hz. CLI `--raw-tree`, TOML `raw_tree`.
- **Sharing the contract (v1.30, TODO/080 D-8)**: Stage 4 of the gas-pressure simulation `~/test/gas-pressure-test` (Geant4 + Garfield++ + AGET
  response, a separate repo) writes `_raw.root` with **the same contract as this section** (`eventId/i`, `eventTime/l`, `adc[4][68][512]/S`), and
  shares `macros/` as `external/tpcdaq-macros/`. **When changing the contract, fix both repos at the same time**. The simulation's
  synthetic raw (with truth) is the fixture source for the §5.5 QA reconstruction, and the forward response (Magboltz diffusion ⊗ AGET shaping) becomes the origin of the
  response kernel for Unfolding (WARSAW_PLAN §7).

## 7. graw-writer specification

- RawFrames from the receiver are appended **byte-for-byte to a file per (cobo, asad)** (v1.1 correction).
  One frame = one AsAd's worth (§2.4), so dispatch only requires reading the asadIdx of the frame header.
  No re-serialization or conversion (the per-AsAd concatenation = the same as the sequence obtained by sorting the input by asadIdx =
  a file readable by grawToEventTPC (TPCReco) / graw2root (GET) / CoBoFrameViewer).
- **Only frames of frameType 1/2 are dispatched** (v1.2). The asadIdx is read with `peek_asad`, which is
  centralized in the decode module (**returns Some only for frameType 1/2 with a header of at least 28 B**) — if offset 27 were read without
  looking at frameType, a control frame longer than 28 B would be **mixed into a wrong AsAd file**.
- **Non-AsAd frames (peek_asad = None. Example: the 12 B frameType 7 topology at the head of the real 2025 run) are
  preserved byte-for-byte in `run{run:04}/ctrl/CoBo{K}_{TS}_{idx:04}.graw`**, and made visible with the `ctrl_frames` counter +
  an info log (v1.2 user decision). **It does not go to the Error state** (a normal control
  frame that arrives at the head of every run must not drop it into Error. Error is only for write failure, seq gap, and run change before EOS).
  The real-machine FrameStorage warns about and discards the same frame (`"Dumping frame"`), but tpcdaq-rs gives priority to the absolute rule
  (no intentional drops). ctrl/ is a subdirectory, so it is invisible to the offline `CoBo*` glob,
  and the per-AsAd files stay exactly identical to the real machine. TS, idx, and rotation rules are the same as for per-AsAd.
- The number of AsAd is hard-coded neither in the configuration nor in the code. A file is created lazily for each observed (cobo, asad)
  (mini = 1 file; ELITPC = **1 CoBo × 4 AsAd = 4 files** appear naturally —
  confirmed on real 2022/2026 data, v1.7).
- **Naming = exact match with the real-machine DataRouter** (v1.1): `CoBo{K}_AsAd{A}_{TS}_{idx:04}.graw`.
  TS = the creation time of the first file of that (cobo, asad) stream, ISO 8601 extended in **localtime** +
  3-digit milliseconds (example `2022-04-12T08:03:44.531` — with colons, Linux assumed). K/A are decimal without zero padding.
  Origin = GET `GetBench/src/get/daq/FrameStorage.cpp` (`"CoBo"<<K<<"_AsAd"<<A<<'_'<<TS<<'_'
  <<setw(4)<<idx<<".graw"`) + `utl::buildTimeStamp()` (localtime + %03d ms — confirmed against the real source 2026-08-13).
- **Rotation keeps the TS fixed and only does idx++** (the same behaviour as FrameStorage `createNewFile(newTimeStamp=false)`).
  A new run gets a new TS + idx=0000. The TS differing by ms between AsAd is the same on the real machine
  (real-data example: AsAd0–3 = .531/.533/.536/.540), and TPCReco `RunIdParser` tolerates it.
- File handles stay open during the run (per-frame open/close is forbidden — the failure of the old DataBloc).
  flush every 1 second, fsync at rotation and close.
- Rotation (**corrected to match the real machine in v1.7**): **after** writing a frame, if the file size
  **strictly exceeds** `max_file_size (default 1 GiB = 2^30 B)`, the next-seq file is opened
  immediately (identical to FrameStorage.cpp:190-197 `write → tellp() > 1024 MiB → createNewFile`).
  **A frame that straddles the boundary stays in the current file** (confirmed on real data: each _0000 = 3852 frames =
  1,073,875,968 B > 2^30. The "check before writing" up to v1.6 was an error that is off by one frame from the real machine).
  **A frame is never split across files**. Even a huge single frame is written whole, and then
  rotation follows. If the run ends right after, an empty next file remains (same behaviour as the real machine).
- A write failure is an Error state + counted (silent is forbidden). Disk full during a run goes through the abnormal-stop path of §1.4-3.
- Run boundary: when the run_number of a Batch changes, a new file set is started; at EOS, flush+close.
- **Leftover frames of the previous acquisition are also preserved (v1.46, TODO/110)**: the old frames that arrive at the head of the first run after zCoBo continued
  acquiring with ECC absent (§1.3 — both eventIdx and CoBo time continue from the previous run) are also written by graw-writer as is without distinguishing them
  (the real-machine DataRouter also writes the same byte sequence = the contract of exact offline match. Lossless). Their count is visible in the decoder's
  `frames_before_restart` (§2.3 → §9.2 `run_stop.counters`), and the handling on the ROOT side is in §6.3.

### 8.1 controller

- **REST API (axum)** — the sole operating surface of the UI. Main endpoints:
  - `GET /api/status` — state of all components + run info + ECC state (equivalent to delila-rs SystemStatus)
  - `POST /api/control/acquire {operator, passphrase}` → `{token}` / `POST /api/control/release`
    — control authority is always held by 1 client. Acquisition can always preempt (C++ version CommandRouter scheme); preemption goes to the audit log
  - `POST /api/run/start {token, comment?}` / `POST /api/run/stop {token}` — executes the sequence of §1.3.
    **The 200 response of run/start (v1.46, TODO/132)** = `{run, phase: "Running", params_id: string | null, notes: string[]}`.

    When current.json overrides the config_id of the TOML (= `params_id` is non-null), `notes` always contains one line:

    **different** from the TOML's configure config_id, and `info!` when it is the same. The response on failure (4xx / 5xx) is unchanged.
    Rationale = an operational trap found in 078 (current.json (pulser) from the previous test was left in place, and a run intended to be "pedestal" ran, which
    could not be told from the response).
  - `POST /api/ecc/{describe|prepare|configure|start|stop|breakup|reset} {token}` — stepwise operations
    (R6: the same operating feel as the GET controller)
  - `GET /api/logbook?since_seq=N` / `POST /api/logbook/comment {author, text}` (R11)
  - **Parameters (v1.33, §3.3, TODO/078)**: `GET /api/params` → `{id, sha256, exceptions, params, files: {configure, prepare}}` (404 if none) /
    `PUT /api/params {token, params}` → same shape (validation failure 400 + `ParamsError` message, 409 while Running, 503 if `ecc_config_dir` is unset) /
    `GET /api/params/render?template=<name>` → `{id, exceptions, configure_xcfg}` (dry run, writes nothing). `GET /api/status` gets `params: {id, exceptions} | null` (null on failure + `notes`).
    **v1.36 (TODO/111)**: `GET /api/params/templates` → `{templates: [string]}` (`configure-*.xcfg` directly under `ecc_config_dir`, in lexicographic order) / `GET /api/params/defaults?template=<name>` →

### 8.2 ecc-bridge (Rust — v1.35. Up to v1.34 it was C++, removed in TODO/076 Phase 3)

- `src/bin/ecc_bridge.rs` = a thin process that puts a JSON REQ/REP server over `src/ecc/{core,proxy}.rs` (port of the state machine, JSON contract, and DataLinkSet XML) + `src/ice/` (the Ice 1.0/1.1 wire) (synchronous, stops on SIGINT/SIGTERM, logs to stderr). Contract, state transitions, and log lines are the same as the old C++ version (457 CHECKs ported, 52 e2e tests, real-machine walk-back match). States: `Off/Idle/Described/Prepared/Ready/Running/Paused/Unknown`.
- Request `{"action": "configure", "config_id": "...", "links": [{"sender": "CoBo[0]",
  "router_ip": "...", "router_port": 46005, "type": "TCP"}, ...]}` → `{"ok", "state", "error"}`.
  `config_id` is **per action, from the start** — the controller passes the **id of the relevant phase** from the configuration of §3.1
  (v1.13. This handles the production practice of using different names for describe/prepare/configure. No change on the ecc-bridge side).
- **`ecc_error` in the status response (added in v1.14, implementation = TODO/043)**: the response to `{"action":"status"}` gets
  the **GET error field** (`NO_ERR`/`WHEN_DESCRIBE`/`WHEN_PREPARE`/…) added as `ecc_error`. The existing `error` remains the transport/bridge-layer error string and its meaning is unchanged.
  The controller `/api/status` passes it through as is (UI display is P4).
  Rationale: the real ECC carries an error flag separate from the state after a failure (e.g. `IDLE / WHEN_DESCRIBE`), but with the
  current status it is invisible from the UI (041 D-1 measurement).
- The DataLinkSet XML is generated from links (1 DataLink per CoBo). **Real-machine traps are fixed as specification**:
  DataSender id is in `CoBo[k]` form, flowType is uppercase `TCP`, Ice encoding fixed at 1.1.
  router_port is the **port the receiver actually bound**, which the controller takes from the Arm response and passes along.
  **flowType stays TCP by ruling (v1.23, TODO/067) — FDT is stated explicitly as unsupported**. The FDT wire
  differs from plain TCP (GetBench primary source): a 4 B IMALIVE `00 00 00 00` immediately after connection
  (FdtDataSender.hpp:125), the same 4 B every time events are absent for 3 s (heartBeatPeriod_ms=3000),
  a 4 B GOODBYE `FF FF FF FF` at daqStop + **socket close (= reconnect for every run)**,
  and a topology frame (frameType 7) sent at daqStart. These 4 B control words are not
  MFM frames, so the current framer reacts by discarding the buffer. **If FDT becomes necessary in the future, open the following
  three-item set as a new unit: ① remove IMALIVE/GOODBYE ② connect/disconnect per run ③ add the same behaviour to vcobo** (note that
  frameType 7 really exists at the head of the graw of the real 2025 mini run — suggesting the link at that time may have been FDT. Whether the TCP path has a topology frame is
  to be settled on site in 069 Q1). The decoder's frameType 7 defence (v1.23) works harmlessly on either path.
- All exceptions are turned into Result (never throw). ECC unreachable is `state: "Unknown"`.
- **Timeout semantics (made explicit in v1.20 — settled by the 057 investigation)**: the controller's ECC REQ is
  **60 s per request** (rcvtimeo. That it fires was fixed by measurement with a delayed fake ECC —
  tests/controller_ecc_timeout.rs). **No deadline is deliberately set on the whole sequence such as run/start** — including walk-back at most 9 REQ = worst case 540 s. The ECC walk is a stateful
  sequence, and abandoning it midway is more dangerous (non-idempotent). The client recovers with its own timeout + `/api/status`
  polling (the UI already works this way). Implication of the measurements: the real ECC's configure
  can take minutes on a cold start (261 s observed in 056) — the time taken by each REQ is always recorded as `elapsed_ms` in the
  controller log's `ecc command applied`.

## 9. JSONL logbook specification (Q1 settled)

### 9.1 File and writer

- Path: `<output_root>/logbook.jsonl` (a single file, append-only. At most a few hundred lines per day,
  so no rotation is needed — cut it yearly if it ever becomes necessary).
- **The controller is the only writer.** Other components (psu, future posters) post through the §2.3 LogPost
  (PUSH/PULL), and the UI posts through REST. The controller adds `ts` (RFC3339, milliseconds, with offset)
  and `seq` (monotonically increasing u64) and appends 1 line = 1 write(2), flushing per line.
- Crash tolerance: corruption of the last line can happen (the only tolerated case) — readers are specified to
  "tolerate a parse failure on the last line only and show a warning".

- Run metadata is not managed twice (the JSONL is the sole run ledger. The run number appears in the ROOT/graw files
  themselves only in the file name).

### 9.3 slowctl time series (InfluxDB, v1.41 — TODO/122, user ruling)

Instead of writing periodic values to the logbook (§9.2), slowctl writes **every sample** to InfluxDB (2.x OSS; 2.9.1 at ELITPC). If `[slowctl.influx]` (§3.1) is absent, nothing is written.

**Position**: the InfluxDB series belong to the **monitoring path** (gaps are tolerated and counted. The retransmit buffer is in memory, and what is lost when slowctl stops or restarts appears in `influx_points_dropped`). The **authoritative record of a run is §9.2** (JSONL single writer = lossless): the `slow` snapshots of run_start / run_stop and IDENT / ALARM / RECOVER / ERROR. InfluxDB is for analysis and post-hoc investigation. The latest values in the snapshot follow the VALUE posting rule (2 % / `log_every_s`), so **they are up to `log_every_s` old and do not include changes smaller than 2 %** (freshness can be read from the per-value `ts`).

- **API**: `POST {url}/api/v2/write?org={org}&bucket={bucket}&precision=ms`, `Authorization: Token {token}`, body in line protocol (3.x also accepts this API).
- **Shape**: for each poll, one line per device and ch. measurement = device name (the TOML `name`), tag `ch` = the node number (a whole-device sample is `ch=board`),
  fields = a float per param plus `alarm` (bool, true if any of the line's values is in alarm), timestamp = the sample's ts (ms). IDENT strings are not written (they are in the logbook).
  Examples: `hv,ch=0 vmon=341.06,imon=9.593,status=33,vset=350,iset=15,alarm=true 1760259600000` / `lv,ch=1 volt=3.6,curr=0.997,outp=1,vset=3.6,iset=2.5,alarm=false …`
- **Units (fixed per param, not held in a column)**:

  | device (type) | param | unit |
  |---|---|---|
  | hivolta | vmon / vset | V |
  | hivolta | imon / iset | µA |
  | hivolta | status / bdalarm | bit mask (DT1415ET STATUS / BDALARM, an integer value as a float) |
  | hivolta | bdilk | 0 / 1 |
  | hmp2020 | volt / vset | V |
  | hmp2020 | curr / iset | A |
  | hmp2020 | outp | 0 / 1 |

- **Writing does not stop reading** (monitoring path — may drop but counts):
  - The path is device_loop → bounded channel (`try_send`; if full, count and drop) → one writer thread (POST every `batch_ms`).
  - A failed batch is returned to a bounded retransmit buffer (`buffer_max_points` points, a point = 1 sample) and retried with exponential backoff 1 → 60 s. When the limit is exceeded, the oldest are dropped and counted.
  - NaN / inf are counted and dropped. On shutdown it flushes once, and what could not be written is counted.
  - The counters are `influx_points_written` / `influx_points_dropped` / `influx_write_errors` / `influx_last_error` in the `counters` of the status PUB.
  - Real hardware (122): no loss even when InfluxDB was stopped for 60 s (the 572 points from the outage were written after recovery).

## 10. WS protocol specification

### 10.1 Binary framing (inherited from the C++ version)

Common 13-byte header for all binary messages (little-endian):

| off | size | content |
|---|---|---|
| 0–1 | 2 | magic `'T' 'P'` |
| 2 | 1 | msgType |
| 3 | 1 | version = 2 (version bumped because the types were redefined) |
| 4 | 1 | flags (bit0 = incomplete event) |
| 5 | 4 | u32 runNumber |
| 9 | 4 | u32 eventNumber (0 for histograms) |

### 10.2 Binary message types

| type | name | body |
|---|---|---|
| 0x02 | `Uvw` | `u8 plane(0=U,1=V,2=W)`, `u16 nStrips`, `u16 nBuckets`, `u16 ADC × nStrips×nBuckets` (strip-major: `idx=(strip-1)*nBuckets+bucket`). **v1.49**: if `[system] ped_table` exists, the missing cells of fragments that look like ZS are filled with the round(mean) of the table (§5.4). Otherwise 0 |
| 0x03 | `Waveforms` | `u8 cobo`, `u8 asad`, `u8 nAget(=4)`, `u8 nCh(=68)`, `u16 nBuckets`, `u16 ADC × nAget×nCh×nBuckets` (aget-major, raw ch order, FPN included, no subtraction — R13) |
| 0x10 | `Histo1d` | `u16 id`, `u32 nbins`, `f32 xmin`, `f32 xmax`, `f32 × nbins` |
| 0x11 | `Histo2d` | `u16 id`, `u16 nx`, `u16 ny`, `f32 xmin,xmax,ymin,ymax`, `f32 × nx×ny` (iy outer, row-major) |
| 0x04 | `Track` (v1.45) | **UTF-8 JSON** (the only one in §10.2 — because the shape grows with multiple tracks and vertices): `{ok, reason, hits:[nU,nV,nW], unplaced, tracks:[{phiDeg, dir, start, end, startF, endF, length, lengthF, xyLength, charge}], points:[[x,y,t,q,view,track],…]}`. The z of start / end and the z of dir are in mm (the macros' default conversion), `t` is the time bucket. The UI tolerates unknown keys, and broken JSON is counted as `bad-json`. **Carried in the live broadcast** (not on the JSON text path) |

- The old 0x01 Event (3D point cloud) is **abolished** (R5 out of scope). **It is not revived for the §5.5 (v1.25)
  QA reconstruction either** — its content is not a point cloud. QA aggregates are carried in the **id 20s** of 0x10/0x11 (source = monitor,
  sampled stated explicitly), and 0x04 `Track` will be opened as a ticket when overlaying tracks on the event display becomes necessary. -> **(v1.45) opened** (the table above, TODO/127).
- Histogram ids match the table in §5.2 (1–3 are 2D, 4–9 are 1D). Bin values are reduced to f32 (display only. The true values
  are on the monitor.root side).

### 10.3 JSON text messages

| type | direction | content |
|---|---|---|
| `meta` | S→C (on connect and on run change) | `{nBuckets, planes: {U,V,W}, geometry, anglesDeg, detector, cobos, run}` |

| `run` | S→C (on transition) | `{state, run, ts}` |
| `stripGeometry` | S→C (once on connect, right after `meta`. v1.43) | `{padPitch, stripPitch, rangeXY, planes:{U,V,W:{unit,pitchUnit,segments}}}` or `{unavailable}` (TODO/125) |

- Operations (cmd/ack) are **not carried** on the WS (a change from the C++ version). Operations are unified on the controller REST (§8.1).
- The server's send queue is drop-oldest + count for live (0x02/0x03/0x04/0x10/0x11) and reliable for JSON control
  (the policy of the C++ SendQueue, this time actually wired up).

### 10.4 Cross-language conformance test (method carried over)

1. **Generator** (Rust bin `tools/ws_proto_sample`): encodes every message type with known values using the production encoder
   and writes a concatenated stream of `u32 length + payload` to a file.
2. **Verifier** (TypeScript, a test that imports the Angular UI's **production decoder**): splits and
   decodes the same file and compares with the known values (floats with ε=1e-5).
3. CI wiring: generate inside cargo test -> verify with node/vitest (the fixture is regenerated every time and not committed —
   the C++ ctest FIXTURES approach, in which staleness cannot structurally occur).
4. Independent layout tests on each language side (Rust: byte-offset asserts / TS: decoder unit tests) are placed alongside.
5. For the live path (receiving meta→uvw→histo→status over a real WS connection and verifying it mechanically), a probe is prepared in P3.

### 10.5 HTTP for analysis (v1.46, TODO/123)

- The monitor (the `[monitor] ws_listen` port, the same axum router as the WS) has **`GET /api/last-event`** in addition to the WS
  (GET only. A read-only surface for the analysis team to fetch the latest event from external scripts — no operations are carried, §8.1).
- Response 200 = the **last built event received** from root-sink (the `built_event` of §5.3, already thinned by `event_publish_hz` =
  latest-first on the monitoring path, not every event) as JSON:
  `{run, event_idx, complete, received_unix_ms, age_ms, fragments: [{cobo, asad, event_idx, event_time, frame_type, revision,
  read_offset, status, mult, window_out, last_cell, n_aget, n_ch, n_buckets, items_out_of_range, adc}]}`
  (fragment order = ascending (cobo, asad) of §6.3).
  - `adc[aget][ch][bucket]` (`n_aget × n_ch × n_buckets` = 4 × 68 × 512) is the **raw ADC (FPN included, no subtraction, same ordering as the 0x03 Waveforms)**,
    and positions that were not read are **`-1`** (distinguished from ADC 0). Out-of-range items are discarded and counted per fragment in `items_out_of_range`
    (not silently).
  - `received_unix_ms` = the time the monitor received it, `age_ms` = the time elapsed up to the response. `last_event` is kept thereafter once even one
    has been received since process start (it is not cleared across runs — read the staleness from `age_ms` / `run`).
- If not even one has been received since process start, **404 `{"error": "no event received yet"}`**.
- `Access-Control-Allow-Origin: *` (allows hitting it directly from a browser. No authentication = the two-layer discipline of the viewing side, §8.1).
- Conversion to JSON is done **only when a request arrives** (monitoring path. It puts no load on the normal path or the acquisition path). The number of requests is the monitor counter
  `last_event_requests`. Measured (ELI-NP mini, run 70): response ≈ 545 kB / 36–40 ms, `items_out_of_range=0`, unread cells 0 (all channels read out).

The final permission is on the device side: DT1415ET must be REMOTE with the front-panel ch switch ON (a DIS flag is refused), and for HMP2020 `OUTP ON` turns the selected ch and the output ON simultaneously, so before/after of both channels are returned. The only path is controller -> slowctl over a **localhost REP (`cmd_bind` / `slow_cmd`, both omitted = disabled)**; direct ZMQ from the UI stays forbidden as in §2.6.

Design discipline: follow Atlassian Design; the monitor is Grafana-style dark. Destructive operations use a confirmation pattern.
freeze is display only and must not be visually confused with run Stop (§5.4).

## 14. Differences from PROPOSAL v0.4 (from the survey — candidates for updating the authoritative v0.5)

1. **Downward revision of the reuse of eb_core**: the delila-rs eb_core merge is timestamp-based with a single global
   buffer, and no implementation exists that matches the description in PROPOSAL §5 of "per-source FIFO -> merge by eventIdx".
   The eventIdx builder is a new implementation (§6.3). What is reused is the skeleton (§6.1).
2. **Change of the event source for the monitor**: drop the direct decoder -> monitor connection and unify on root-sink's built-event
   publish (§1.2). The PROPOSAL's architecture diagram needs updating.
3. **run_number is carried on every data batch** (an improvement over the delila-rs approach, §2.2).
4. **Back-pressure scheme**: not delila-rs's "HWM=0 unbounded buffer" but a finite HWM + bounded queue + a visible Error
   (§1.4). A concretization of the PROPOSAL's "protect with PUSH/PULL back-pressure".
5. **No .dat for the ELITPC 2-CoBo exists** (all 13 variants in the TPCReco repository have only COBO 0 and 4 ASAD).
   GeometryTPC itself supports 2 CoBo. Moved to the confirmation items of §13-7
   (v1.7: settled as "not needed" by the real data — the wire reality is exactly COBO 0 and 4 ASAD).
6. root_sink **does not write histograms to a file** (THttpServer live only) — the R10 implementation is new code.
   PROPOSAL §5 "reuse root_sink's TH1D/TH2D writing mechanism" is more accurately "reuse the registration/creation mechanism, the writing is
   new".
7. The C++ tpcdaq has the run number hard-coded to 0 and writes no run metadata at all (confirming that the JSONL design §9 is
   the new part that fills this gap).
8. **Redefinition of the position of R8 "graw2root-compatible ROOT" (v1.19, user ruling 2026-08-16)**:
   PROPOSAL R8 defined the ROOT path as "online reproduction of the compatible output", and this is extended to
   "**analysis-ready products**" (on top of the compatible PEventTPC, processed derivatives such as Unfolding and gain normalization may be added).
   The distinction that **raw data is graw only** is made explicit
   (§6.4 v1.19). The origin is the 3 requests of Prof. Wojciech at Warsaw (WARSAW_PLAN §7).
