## 1. 背景

GET ベースの現行 DAQ には以下の実運用上の不満がある(詳細は `ASSESSMENT_移植検討.md`):

1. **オフライン変換の時間の無駄** — graw → ROOT(graw2root)を実験後に回しており、待ち時間が発生する。
2. **オンラインモニタが後読み構図** — TPCReco が「ディレクトリに書き出された graw ファイル」を読む方式で、
   リアルタイム性がない。また我々の確認の範囲では **TPCReco のオンラインモードはトラック再構成を
   含まない**と理解している(2026-08 確認。誤りがあれば訂正いただきたい)。オンラインで実際に必要なのは
   軽量なヒストグラム表示であり、再構成つきモニタは不要。
3. 受信〜保存が単一スレッド同期という設計上の弱さ。
   > 注: かつて安定性問題として疑っていた「~1000 トリガーで停止」は、後に **VETO の誤入力が原因と判明**
   > (2026-08)。**ソフトウェア起因ではなかった**。調査時に見つけた DataBloc 64MiB バジェットの単調消費
   > (`ASSESSMENT_移植検討.md` §1-2)はコード上の潜在問題としては残るが、本提案の動機からは外す。
4. **操作系がアプリごとにバラバラ** — run 制御(GetController)、電源操作、モニタがそれぞれ別の
   起動物で、シフトのたびに複数アプリを立ち上げる。**「いくつものアプリの起動を 1 つに集約する」ことが
   本プロジェクトのキーポイントの一つ**(run 制御統合も R12 の電源統合もこの方針の帰結)。

2026-06 に C++ で新 DAQ(`tpcdaq/`)を M4+ハードニングまで実装済み(24/24 テスト緑、実 2025 .graw 回帰
一致を 2026-08-06 再検証)。テストはすべてソフトウェアテストで、**実機(実 CoBo/実 ECC)との接続は
未実施**。ただし通信プロトコル起因の実機ブロッカー 3 件 — 実 2025 run の frameType 2(compact)非対応
(events=0 → 対応後 108)、DataSender id 形式(`CoBo[0]`、flowType 大文字 `TCP`)、Ice encoding 1.1 固定 —
は実データ・実 GET ソースとの突き合わせで修正済み(`tpcdaq/README.md` ハードニング節に記録)。
今回 HIGS での実験参加で得た所感を基に要求を更新し、方針を再定義する。

> R4 の定義(2026-08-10 確定): x 軸 = チャージ(ADC 波高)。各ストリップの信号はチャージ積分の
> 時間分布として来るので、その**時間方向最大値**を「波高」とする。①は 1 イベントで N_strip エントリ
> (ノイズも山ごと記録される — 低い側は表示/解析時にカットすればよい)、②は 1 イベント 1 エントリ。
> **run start でリセット**し、run 中は全イベントを積算。run stop 時の書き出しは R10。
>
> **主目的は飽和監視** — 最大値が ADC 天井(12bit = 4095)に張り付いていないかを見るのが第一。
> この目的では①②はほぼ等価(両方とも低コストなので両方実装)。したがって x レンジは**フル ADC
> スケール(0–4096)固定**とし、天井ビンが常に見える形にする(オートレンジで天井が隠れる UI は不可)。
> 補助として面毎の**飽和率**(波高 = フルスケールだったストリップの割合)の数値表示も安価で直接的
> なので仕様書段階で検討。

## 3. スコープ / 非スコープ

**スコープ**: データ面まるごと(受信 → デコード → 保存二系統 → モニタ)+ run 制御 + Web UI。
**最初からフル DAQ 置換を狙う**(dataRouter を新アプリに向ける。ファイル追尾モニタ等の中間形態は主目標にしない)。

**非スコープ**:
- オンライン 3D/XY 再構成表示(R5)
- TPCReco・オフライン解析チェーンの変更(ROOT 出力互換で無改造接続が目標)
- 制御プレーンの中身(ECC/getHwServer/FW)の変更 — クライアントとして話すだけ
- Mac/Windows 対応(運用は Linux。開発は Mac 可)

## 4. 基本方針(決定事項 2026-08-10)

| 決定 | 内容 | 理由 |
|------|------|------|
| D1 | **新規 Rust プロジェクトとして独立させる**。名前は **`tpcdaq-rs`**(仮) | DAQ として delila-rs とは毛色が違いすぎる。C++ 版 `tpcdaq` からの系譜が名前で分かり、delila-rs と同じ命名規則 |
| D2 | **コアは Rust、エコシステムに縛られる部分だけ C++ サテライト** | ROOT(イベント TTree・モニタヒストとも書き出しは C++ 必須 — oxyroot 再検証 2026-08-12、§5)と ZeroC Ice(ECC 制御)は C++ が事実上必須。それ以外を Rust に |
| D3 | **最初からフル DAQ 置換を狙う** | 価値の中心(オフライン変換の廃止・リアルタイムモニタ)は置換しないと出ない |
| D4 | **delila-rs と同じコンポーネントシステムを踏襲、コンポーネント間通信は ZeroMQ** | 実績あるアーキテクチャと実装ノウハウを流用。C++ サテライトも「ZMQ を話す一コンポーネント」として自然に接続できる |
| D5 | **開発はまず単独で進め、ELI-NP 側で mini TPC を使った実機テストによる動作検証を徹底的に行った上で、使える段階になったら Warsaw 側でテストしてもらう** | 方針調整のオーバーヘッドなしに速く形にでき、実機検証(mini TPC)は ELI-NP で自前で回せる。Warsaw には検証済みのものを渡す。ELITPC は先方にある。**開発作業はソロで進めるが、仕様・要求への意見はこの段階から歓迎**(本書の配布がその第一歩) |

### D2 の含意 — 「Ice も C++ 側」

2026-06 の中断理由は「Ice を Rust でやるのが面倒」だった。本方針ではこれを構造的に回避する:
**Rust コアは Ice を一切知らない**。ECC との Ice 通信は既存 `tpcdaq::control::EccController`
(状態機械ラッパ、Ice を pimpl 隠蔽済み)を小さな C++ ブリッジに切り出し、Rust からは
プレーンなプロトコル(JSON over stdio/socket)で駆動する。ROOT 書き出しは delila-rs の
C++ コンポーネント **root_sink**(ZMQ 購読 + イベントビルダ eb_core + TTree/TH1/TH2 書き出しの
実績あり)を骨格として流用し、TTree の中身は既存 `RootWriter`(GDataFrame、graw2root 互換
検証済み)から移植する。

## 5. アーキテクチャ案 — delila-rs 型コンポーネントシステム(ZeroMQ)

delila-rs で実績のあるコンポーネントシステムを踏襲する(D4)。機能単位の独立コンポーネントを
ZeroMQ で接続し、C++ サテライトも「同じ ZMQ プロトコルを話す一コンポーネント」として参加する。

```
CoBo ──TCP:46005──▶ [receiver] ──ZMQ──▶ [graw-writer]                 ← ロスレス(byte 一致 append)
                        │
                        └──ZMQ──▶ [decoder] ──ZMQ──┬──▶ [root-sink (C++)] ← ロスレス(イベントビルダ + graw2root 互換 TTree + monitor.root)
                                                    └──▶ [monitor] ──▶ WS ──▶ Web UI(ブラウザ)
                                                          ▲                 ・面別 strip×time 2D ×3
                                                          │ run 通知         ・面別チャージヒスト 2種×3
[controller] ──ZMQ──▶ [ecc-bridge (C++)] ──Ice──▶ ECC:46002 ──▶ CoBo(getHwServer)
     └── run メタデータ記録(JSONL)
```

- **止めない原則**は C++ 版と同じ: receiver は drain のみ。保存系(graw-writer / root-sink)は
  ロスレス(PUSH/PULL の背圧で守る)、モニタ系は最新優先(PUB/SUB + 間引き)。「保存と可視化の分離」
  (C++ 版ハードニング C3 の教訓)をコンポーネント境界として最初から設計に入れる。
- **listen-before-start**(`ecc start` 前に 46005 を listen)等、M4 で確定した運用不変条件を引き継ぐ。
- ELITPC/mini はジオメトリ設定(TPCReco の `.dat` 形式)で切替。**ch 数をコードに焼き込まない**
  (C++ 版は mini=256ch 前提が入っており、ここは新規に設計し直す)。
- **複数 CoBo を最初から設計に含める**(ELITPC は 4 AsAd = **2 CoBo** 構成 — R2 — なので将来保険では
  なく**本番要件**。手元で検証できるのは単一 CoBo〔mini = 1 AsAd〕のみだが、構成ファイルで N 台に
  拡張できる形にする): receiver は CoBo 毎に 1 コンポーネント。**生 graw は CoBo 毎に別ファイル** —
  ストリーム毎の順序は TCP が保証するので、ファイル内順序は構造的に常に正しい。CoBo をまたぐ統合が
  必要な出力(ROOT/モニタ)にだけ**イベントビルダ**(ソース毎 FIFO → eventIdx でマージ、欠け
  フラグメントはタイムアウトで不完全マーク。単一 CoBo 構成では素通し)を挟む。実装は
  **delila-rs の C++ root_sink(eb_core)を流用**(§9)。**ビルド後のイベントデータは run 毎に
  単一 ROOT ファイルを目標**とし(run 番号・イベント番号の整合性はビルダが保証)、CoBo 毎に
  分けるのは生 graw のみ。
  > 参考: 現行 GET で Warsaw が直面中の「CoBo/AsAd 毎のファイルは順序正常、全部まとめて 1 ファイルに
  > すると順序が狂う」問題は、独立 TCP ストリームを**到着順で連結**していることが**原因の最有力候補**
  > (ストリーム間の到着順は非決定的で、イベント番号での再順序化 = イベントビルダなしでは混ざるのが
  > 正常動作)。ただし**未検証の仮説**なので断定しない — 発生単位の確認(Q3)と併せて裏取りする。
  > いずれにせよ上記の設計はこの種の順序問題を構造的に回避する。
  > ELITPC = 2 CoBo(R2)なので、イベントビルダは ELITPC では**必須**(素通しで済むのは mini
  > 〔1 CoBo〕のみ)。手元実機は mini だけのため、**多ソースマージは graw_replay ×2 並走の
  > オフライン試験で Warsaw 前に固める**(§7)。現行問題の発生単位(CoBo 毎ファイルか AsAd 毎か)の
  > 確認は Q3(§10)— 1 CoBo = 1 独立 TCP ストリームなので CoBo 単位と推定。
- コンポーネント化の副産物: 将来のオンラインフィルタは decoder と writer/monitor の間に
  一コンポーネント挿すだけで済む。ホストをまたぐ分散配置も ZMQ なら自然にできる。
- 各リンクのメッセージ形式(生フレーム/デコード済みイベントのシリアライズ)は仕様書段階で
  delila-rs の形式に合わせて定義する。C++ サテライトの接続形態の問題(プロセス分離 vs FFI)は
  ZMQ コンポーネント化により自動的に解決(全部独立プロセス)。
- **run stop 時のモニタ書き出し**(R10): stop を受けたらヒスト群を速やかに
  `run<N>_monitor.root`(ヒストのみ・イベントデータとは別ファイル)へ書き出す。C++ 版 M3 の
  monitor.root 方式の継承。書き出しは **C++ 側(root_sink の TH1D/TH2D 書き出し機構を流用)**。
  当初「Rust から oxyroot で直接(確定)」としていたが、**再検証(2026-08-12)で撤回**: oxyroot
  (0.1.25)の公開 API にヒストグラム型が存在せず(write は `WriterTree` = TTree 基本型ブランチ・
  非圧縮のみ)、最小テストで TTree 書き出しは成功・`TH1D` はコンパイル不可を実証。delila-rs でも
  Rust/oxyroot が書いているのは TTree のみで、ヒストを書いているのは C++ root_sink 側だった。
  **ヒスト集計の持ち主は仕様書の最初に決める最重要設計判断**: Rust monitor と root_sink の
  二重集計は「UI で見た形と monitor.root が一致しない」リスク(ビニング・リセットの二重管理)、
  root_sink への一元化は可視化負荷が保存系プロセスに同居し C3「保存と可視化の分離」の教訓と
  緊張する。候補: root_sink が集計してヒストスナップショットを publish し、monitor/UI は表示に
  徹する(不一致は構造的に消えるが、保存系の負荷分離〔別スレッド化等〕の検証が条件)。
- **イベント表示の更新制御はクライアント側**(R9): サーバは常に最新イベントを配り続け(PUB/SUB
  最新優先)、表示間隔(0 秒 = 真のリアルタイム)と freeze は各ブラウザが独立に適用する。
  → コア無改造で実現でき、誰かが freeze 中でも他のクライアントはライブ更新を継続できる。
  **freeze が止めるのは表示のみ**で、DAQ・積算ヒスト・保存は一切止まらない(UI 上も run の
  Stop とは明確に区別する)。配信イベントには**イベント ID(run 番号 / イベント番号)**を
  常時付与して画面に表示する — イベント番号は MFM ヘッダの eventIdx をデコーダが運ぶだけなので
  実装コストはほぼゼロで、「面白いイベント発見 → ID 控え → オフライン精査」の動線が繋がる。
- **波形ビュー**(R13): R9 のイベント表示と**同一のイベントペイロード**を使う UI ビュー(コア無改造で
  追加できる)。表示中イベントの全ストリップ生波形(FPN 含む・減算なし — pedestal 用途では FPN と
  ベースラインがそのまま見えることが本質)を、面/AsAd/AGET 単位で重ね描きまたはグリッド表示する。
  interval・freeze・イベント ID(R9)の仕組みがそのまま適用される。ELITPC フルの重ね描きは点数が
  多い(~1088 ch × 512 bucket)ため、表示単位の絞り込みとクライアント側間引きを UI 仕様で定義。
- **アクセス制御は二層**: 閲覧(モニタ)は認証なしで開放(シフト中に誰でも見られるのは機能)。
  操作(configure/start/stop)は ①制御トークン(操作権は常に 1 クライアント、C++ 版 M4 設計を継承)
  ②共有パスフレーズ(config に 1 個、操作権取得時に要求)③操作者名入りの**監査ログ**(全操作を
  run メタデータ R7 に記録)。想定脅威は攻撃者ではなく**事故と競合操作**であり、ユーザーアカウント/
  ロール管理は導入しない。リモートアクセスは SSH トンネル経由(TLS・認証を自前実装しない)。
  コラボが本格認証を要求した場合はリバースプロキシ(basic auth 等)を前段に置いてコード無改造で対応。
- **(おまけ)psu コンポーネント(監視 + 制御)**(R12): 設定ファイルに機器リスト(型・アドレス)を書き、
  1 Hz ポーリング → ZMQ publish → UI の「Power」パネル(ch 毎 V/I トレンド + ステータスバッジ +
  TRIP/ALARM 赤バナー + ON/OFF・VSET 操作)。TRIP/INTLK 等の遷移は R11 ログブックへ自動記録(run と同一タイムライン)。
  - **HiVolta**: TCP:1470 の ASCII プロトコル(`$CMD:MON,CH:8,PAR:VMON` 等で全 8ch 一括読み。
    マニュアル DT1415_rev16.pdf p.23–26)。**モニタは LOCAL モードのまま許可**(SET のみ `#LOC:ERR`)
    → 読み取り専用監視は現場運転に無干渉。TCP は同時 1 クライアント想定 → ポーラー 1 個が専有し
    ブラウザへ fan-out(本アーキテクチャと整合)。公式ツールは「coming soon」のまま・EPICS 廃止
    のため自作の価値が実際にある。
  - **HMP2020**: 標準 SCPI(LAN = raw socket:5025〔HO730/HO732 オプション〕or USB)。
    `MEAS:VOLT?`/`MEAS:CURR?` 定型。リモート時の前面パネルロックは `SYST:MIX`(混在モード)で回避予定。
  - **制御も含める(2026-08-10 決定)**: ELI-NP 側には電源制御アプリが現状存在しないため、監視に加え
    ON/OFF・VSET・ランプ等の制御も実装する(§1-4 アプリ集約方針の帰結)。HV 操作は §5 アクセス制御の
    操作権トークン+パスフレーズ+監査ログの枠にそのまま載せ、UI は破壊的操作の確認パターンを適用。
    設定ファイルの SWVMAX(ソフト電圧上限)で誤設定の上限を機械的に制限。HiVolta の SET は REMOTE
    モードが必要(`BDCTR` で切替。LOCAL に戻せば前面パネル運用に復帰、モニタはどちらのモードでも可)。
  - **Warsaw は制御込みデスクトップアプリを実装済み**(2026-08-10 判明)→ **Warsaw に配備する場合のみ**
    HiVolta の単一 TCP 接続を先方アプリと取り合う問題がある(ELI-NP では競合なし、先行投入可)。
    併用策(我々が USB 側 / 先方アプリにエクスポート追加 / 先方はデスクトップ継続)は配備時に相談(Q2)。
    先方の実装ノウハウ(プロトコルの癖)の聞き取りは調査工数を消すので早めに。
- **ログブックビュー**(R11): run メタデータ(start/stop、configId、出力ファイル、イベント数…)と
  操作監査ログは**同一の JSONL タイムライン**に流れ込むので、UI の「ログ」タブがそれをログブック的に
  表示するだけで「いつ誰が何をし、どの run で何が起きたか」が一覧できる。**シフトの自由記述コメントも
  同じタイムラインに追記できるようにする(簡易電子ログブック化、確定)** — 入れて困ることはない。
  書き手は 4 者(controller の run 記録・操作監査ログ、UI のシフトコメント、psu の TRIP)になるため、
  **JSONL への追記は controller の単一ライタに一本化**し、他コンポーネントは ZMQ 経由で投稿する
  (行混線・順序逆転の防止。仕様書で定義)。

## 6. 性能・データ量見積(最低目標 = トリガー 100 Hz)

現状のトリガーは 4 Hz(ビーム増強しても ~20 Hz)だが、**最低目標は 100 Hz** とする(2026-08-12 に
80 Hz から更新)。背景: ガスターゲットではなく**内部に固体ターゲットを置いてビームを当て、出てくる
粒子を検出する案**が立ち上がっており、Warsaw の Wojciech Dominik 教授が 100 Hz を想定している。100 Hz は
受け入れ基準であって上限ではない — **ソフト側にハードキャップを作らず、天井はリンク・ディスク・
GET フロントエンドの物理側で決まる**設計とする(行けるところまで行く)。

| 項目 | mini eTPC (256ch) | ELITPC (~1024ch) |
|------|-------------------|------------------|
| イベントサイズ(フル readout, 512 bucket × 2B) | ~0.28 MB | ~1.1 MB |
| トリガーレート(最低目標) | 100 Hz | 100 Hz |
| 最大スループット | ~28 MB/s | **~111 MB/s(≈0.9 Gbit/s、2 CoBo 合算)** |
| ディスク(目標レート持続時) | ~2.4 TB/日 | **~9.6 TB/日** |

CPU は依然余裕。ネットワークは、ELITPC の ~111 MB/s が **2 CoBo × ~56 MB/s(CoBo 毎リンク
~0.45 Gbit/s)**に分かれるため CoBo 側リンクは余裕だが、**受信ホストの NIC には合算 ~0.9 Gbit/s が
着信し、1GbE(TCP 実効 ~0.94 Gbit/s)では飽和寸前**。したがって **ELITPC × 100 Hz のフル readout
には、受信側の 10GbE 化か、CoBo 毎に NIC を分ける(receiver は CoBo 毎に独立コンポーネントなので
構造上そのまま可能)かのどちらかが事実上必須**。データリンクは MTU 9000 前提。あわせてゼロ
サプレッション/部分 readout も検討事項に含める。ディスクは目標レート持続で ~9.6 TB/日と本格的な
計画が必要 — 将来のオンラインフィルタ+生データのプレスケール保存(スコープ外だが、§5 の
コンポーネント挿入で後付け可能)がここで効く。
設計の主眼は「止めない・失わない・リアルタイムに見える」の 3 点で変わらない。

> 参考(要実測): フル readout の AGET 読み出しは概算 ~1.4 ms/イベント(68 ch × 512 cell ÷ 25 MS/s)
> で、100 Hz ではデッドタイム ~14%。「行けるところまで」の実効天井はソフトではなく GET フロント
> エンド側で決まる可能性が高く、ハード側の実測は P5 実機検証に含める。さらに上を狙う場合の本命は
> 部分 readout/ゼロサプレッション(イベントを小さくする方向)で、これも §5 のコンポーネント挿入で
> 後付けできる。

## 7. 検証戦略 — 既存 C++ をオラクルに使う

新規 Rust 実装の正しさは、検証済み C++ 資産との突き合わせで機械的に確認する:

1. **デコーダ**: 実 2025 run graw(29MB)で `events=108 / items=15,040,512 / malformed=0` を再現すること
   (C++ 版で確定済みの答え)。frameType 1(2018)/ 2(2025, blkSize256/big-endian)両対応。
2. **graw writer**: リプレイ入力とのバイト完全一致(C++ M2 と同じ判定基準)。
3. **ROOT 出力**: root_sink へ移植した TTree 定義を、同一入力で C++ 版 tpcdaq の出力と TTree レベル
   比較(graw2root 互換の担保 — `RootWriter` からの移植なので答え合わせは機械的)。
4. **WS プロトコル**: UI 新規化に伴いワイヤプロトコルは仕様書で再定義する。ただし既存のクロス言語
   適合性テスト方式(サンプル生成 → 送受双方で機械検証)は新プロトコルにもそのまま踏襲する。
5. **run 制御**: 既存 fake-ECC servant(テストハーネス)相手に e2e。実 ECC はコンテナ → 実機の順。
   実 ECC は**実験で使用中と同一版**(`~/WorkSpace/HIGS/2026/20190315_patched`、2026-08-10 入手)で
   ビルドして検証する。※同版と vendored 版の比較済み: .ice 全 6 ファイル・MDaq・GetController・
   MultiFrame ソース・ポート定義すべて一致(差分は MuTanT 設定 4 ファイルのみ、client 側に影響なし)。
6. **オフライン検証で完結**: `graw_replay` + fake-ECC で検出器なしに全機能を回せる(C++ 版と同じ方式)。
   実機は最終受け入れのみ。複数 CoBo 経路(イベントビルダの多ソースマージ)も **graw_replay ×2 並走**で
   検証する — 実機の 2 CoBo 構成は Warsaw(ELITPC)まで手元に無いため、ここはオフラインで固める。

## 8. ロードマップ(連番 TODO ユニットは着手時に起票)

| Phase | 内容 | 出口条件 |
|-------|------|----------|
| P0 | コンポーネント骨格(ZMQ 配線)、設定読込、ジオメトリ抽象(mini/ELITPC) | ELITPC .dat が読めて ch→(plane,strip) が引ける |
| P1 | 受信(CoBo 毎 receiver、構成で N 台可)+ framer + デコーダ | オラクル一致(§7-1)、リプレイで dropped 0(100 Hz 相当負荷含む) |

| P3 | モニタ集計 + WS + 新規 UI(R3/R4 の 9 ヒスト + R9 イベント表示 + R13 波形ビュー)+ R10 stop 時書き出し | 新 UI でライブ表示、適合性テスト緑、stop で run\<N\>_monitor.root が書ける |

デコード・保存・run 制御(P1/P2/P4)は C++ 版で一度通った道(仕様・テスト・答えが全部ある)、
イベントビルダは delila-rs root_sink(eb_core)の流用。純粋な新規設計は P0 のジオメトリ一般化、
R4 チャージヒスト、P3 の新 UI + 新 WS プロトコル、P6 の psu。P6 は P0–P5 と独立に着手でき、
ELI-NP には競合アプリが無いため先行投入可(Q2)。ただし root_sink の「流用」は骨格であって
本体ではない(TTree 部は移植作業 + ロスレス化改造 — §9 注意書き)ので、P2 を「流用だから軽い」
とは見積もらないこと。カレンダー見積は意図的に未記載(仕様確定前に日程をコミットしない)。
仕様確定後に幅つきの目安を共有する。

## 9. 既存資産の扱い

- `tpcdaq/`(C++): 凍結せず**リファレンス + オラクル + サテライト供給元**として維持。
- delila-rs: コンポーネントシステム・ZMQ 設計・Angular UI パターンの踏襲元。**`tools/root_sink`(C++)**は
  イベントビルダ(eb_core)+ ROOT 書き出し(ZSTD 圧縮 TTree / TH1D/TH2D)の流用元。ただし DELILA 固有の
  イベント形式・Δt モニタ部分は TPC 用に書き直しで、流用は骨格(ZMQ 購読・run 状態・ビルダ・ヒスト
  登録/書き出し機構)。TTree の中身は `RootWriter` から移植(§4 D2)。
  **注意(流用の最大の手術箇所)**: root_sink は元来「merger の PUB を追加購読する**非権威**コンシューマ
  (パイプラインを決して堰き止めない・取りこぼしても良い)」として設計されている(ソース冒頭コメント)。
  tpcdaq-rs では ROOT 保存は**ロスレス系**(§5: PUSH/PULL 背圧)なので、購読側のトランスポート
  意味論を逆転させる改造が必須。
- `reuse/rust_reference/`(geometry.rs / recon.rs): ジオメトリ・FPN リオーダは P0 の種。
  W 整合ゴースト抑制はオンライン非スコープ化(R5)により当面不要。
- webui(素 JS): **流用しない(UI は新規に作る — 追加予定機能が多いため)**。WS プロトコルの
  クロス言語適合性テストの方式だけ新プロトコル設計に踏襲(§7-4)。
