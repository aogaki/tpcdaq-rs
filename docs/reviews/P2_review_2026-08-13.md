## 指摘(重大)

### R1. decoder の 2 ソース飢餓 — ELITPC ブロッカ【**解消済み** — [013](../../TODO/archive/013_decoder_starvation.md) 2026-08-13 完了】
decoder が入力に追いつけないとき片ソースを run 丸ごと飢餓させ、全イベント incomplete 化していた。
**真因(013 が計測で確定 — 当初仮説の tight loop は棄却)**: libzmq の `socket_base_t::recv()` は
`process_commands()` を「成功 100 回に 1 度(`inbound_poll_rate=100`)か EAGAIN 時」しか呼ばず、
fair-queue から外れたパイプの再活性化(`activate_read` コマンド)が取り込まれない。消費が供給より
遅い間は EAGAIN が起きないため、外れた上流は 100 通ぶん戻れない(観測の 101 連続・96 vs 1 の
機構固定テストと数値一致)。**修正 = recv の前に必ず poll**(期限ベース待ち、100 ms 上限、切り上げ)。
dev/release とも E2E-B skip なし green、テスト 226。副次効果: アイドル時の起床 500→10 回/s。
**教訓として横展開**: 複数上流の PULL/SUB を recv だけの loop で回す実装は同罠を踏む —
root_sink は単一上流(SPEC §2.3)なので現状無害だが、**複数上流化する設計変更時は必須確認**。
delila-rs にも該当し得る(メモリに記録済み)。

### R2. frameType 1 の実データ回帰が存在しない
ローカル実 .graw(2025)は frameType 2 のみ。frameType 1(2018 形式)は合成フィクスチャの
CI green だけで、オラクル級の実データ照合が無い。**Warsaw の 2018 実 .graw を 1 run 分
入手するまで、frameType 1 対応は「たぶん動く」の水準**。→ Warsaw 確認事項に追加(CURRENT)。

**クローズ(2026-08-13、TODO/019)**: ELITPC 実データ 2022/2026 を入手して実測した結果、
**2022 時点で既に frameType 2(compact)rev 5** — frameType 1 の実データはそもそも実機から
出てこないと確定。R2 は「frameType 1 のオラクルが無い」ではなく「不要」という形で解消。
frameType 1 対応は合成フィクスチャの保険として維持。frameType 2 の実データ回帰は
`tests/elitpc_real_graw.rs`(`TPCDAQ_REAL_GRAW_DIR`)で両年 green。副産物として
ローテーション境界の実機不一致(書く前判定 vs 実機の書き込み後判定)を発見・修正(SPEC v1.7 §7)。

### R3. run 中止(Reset)のカスケードが未設計
decoder の Reset は送出を打ち切り(可視カウント — 009 の設計どおり)、その結果 root-sink は
seq ギャップで **exit 3(fatal 死)**する。単体としてはどちらも仕様どおりだが、系として
「オペレータが run を中止する正規手順」が下流の fatal 死で終わるのは運用設計として未完。
**P3(controller)の停止シーケンス設計の必須入力**(stop-first-downstream か、root-sink に
run-abort を伝える口か)。現時点は文書化のみ — P3 起票時に本項を参照すること。

## 指摘(軽微・記録のみ)

- graw-writer の flush 1 s + fsync はローテーション/close のみ = 電源断で最大ファイル 1 本分の
  尻尾が飛び得る。プロセスクラッシュでは(カーネルに flush 済みのため)ほぼ無傷。実機 DataRouter
  同等であり、クラッシュ run は無効扱いなので許容。
- root_sink の JSON カウンタは実測でスキーマ安定(012 が機械照合に使用)。将来フィールドを
  増やすときは後方互換(追加のみ)を守ること。
- 011 の AutoSave 30 s は異常終了時の inprogress 救出可能性を上げる副次効果あり — 維持。
